### 断连要重启车机：三个假设，两个已否掉

- **否掉①「SDP 缓存过期/通道号变了」**：失败与成功两次连接的
  `Bluetooth cached uuids=`、`candidates=[phone:UUID_CACHE_HINT, phone-v2:PROBE_ON_UNKNOWN]`、
  `selected initiator=phone; peer matched` **完全逐字相同**，只有时间差 70 秒。
- **否掉②「重试太密把车机计时器顶回去」**：5 次 NO_SYN（每 11 秒一次）之后第 6 次成功，
  说明每次重试**没有**重置车机计时器，它只是自己需要 ~70 秒。
- **仍然成立的现象**：车机 RFCOMM 层立刻接受连接（120ms 内 `peer matched`），
  但应用层永远不回 iAP SYN。研究文档明确「拆除靠平台 socket close，不发 DISC 字节」，
  所以不是我们少发告别报文；AirPlay 层 TEARDOWN 也确实回了 200。
- 用户发现的绕过（切车机通道 CarPlay↔亿联）= 车机侧硬复位，这是目前唯一能立刻恢复的手段。
- `NO_SYN` 抛的是普通 `SocketTimeoutException`，不是 `IapStartupTimeout`，
  所以不会被判成终止错误 —— 重连循环确实在工作。

### 麦克风死机：卡在密钥材料

`Audio category=3 microphone not offered: MFi/SAP input key direction is not implemented`，
每次 SETUP 都是 `input=absent`。研究结论：固件里上行是独立标签

所以 SAP 下麦克风上行不是"没做"，是缺密钥证据；要做得先补研究。

## 13:20 重大修正：车机在 type 100 上只有一个 PCM 上下文

20031 把 PCM 优先扩到 cat 1/2/3，实车（20032，session 3b3e1417）**直接把主音频搞坏了**：

```
cat3  100/speechRecognition  PCM 24k/1  spf=120  → SETUP accepted
cat2  100/alert              PCM 48k/2  spf=240  → status=400 被拒
cat2  101/default            PCM 48k/2  spf=240  → SETUP accepted
cat1  100/media              PCM 48k/2  spf=240  → StatusException，主音频建不起来
```

对照 20030（唯一差别是 cat3 用的是 AAC-ELD 而不是 PCM）：`100/media` + 48k/2 + spf=240 是被接受的。
**结论：车机在 type 100 上只维护一个 PCM 上下文，谁先占住格式谁赢，后面的同类型 SETUP 全部拒绝；
type 101 是独立上下文，所以 cat2 换成 101/default 就能建起来。**

20033/20034 的最终形态：
- category 1 → `100/media` PCM（与实车出声的配置逐字节一致）
- category 3 → **永不 PCM**，留在压缩路径（有回归测试钉住）
- category 2 → `101/default` PCM，但挂在独立开关 `pcmAlert` 后面，默认关

另修两处自身缺陷：
1. `pcmRoutes` 忘了用 `preferPcm` 守 category 1，导致 `preferPcm=false` 失效（4 条测试抓到）。
2. `refreshSdpAfterNoSyn` 原来放在重试循环的局部变量里，而 **CarWith 重新绑定会再调 start()
   起一个新循环** —— 20032 日志里 NO_SYN 之后 320ms 就有新 start()，所以 SDP 刷新永远不触发。

## 13:35 触摸链路：排除描述符，修事件读线程被宿主拖死

**先排除掉的假线索**：20030/20033 日志里三条
`INFO HID #1/#2/#3 touch unsupported: ... No unique complete absolute touch report`
是**正常**的，不是故障。逐字节解了那三个描述符：

- `#1`（43B）`05 0c 09 01` → Consumer Control，媒体键；
- `#2`（67B）`05 0b 09 01` → Keyboard；
- `#3`（74B）`05 01 09 08` → Multi-axis Controller（X/Y 逻辑范围 -127..127 + Rel 滚轮）。

它们本来就没有 Tip Switch（`0x0d0042`），`HidTouch.parse` 要求
`0x0d0042 + 0x010030 + 0x010031` 齐全，所以"不是触摸屏"是正确结论。
真正的触摸屏是 `#0`（62B），解析成功，会话日志 `INFO screen 1024x600 fps=30 touch=true`。

**另一个此前的误判**：`hidSendReport` 在 20030/20033 里**一条都没有**。
但这两次会话分别只有 46 s / 40 s，用户没在车机上操作，所以**不能**据此说触摸从来不通。
说明：`host touch-listener 1` 有，触摸回调 `host::touch` 接线正确（CarPlayRunner.kt:115）。
`hidSendReport` 是**接收端→发送端**的 RTSP 事件（走 `authenticatedEvent`），
iAP 的 `iAPSendMessage` 才是车机→我们的另一条通道，两者不要混。

**真正的问题（代码可证）**：`openEventChannel` 是**单协程串行循环**——
`read → handle → reply`。而触摸注入 `CarPlayHost.touch` 一路同步调
`hostTouch(event)` = `IRemoteTouchListener.onTouchEvent`，
AIDL **没有 oneway**（`host-carlife-mixing/src/main/aidl/.../IRemoteTouchListener.aidl`），
即**同步 Binder**。于是：宿主的 `onTouchEvent` 一旦卡住（CarWith 主线程被语音识别 /
拉起导航占用），事件读线程就停止读取和应答车机，车机输入通道随之死掉，只能重启车机。
这与大哥描述的三条现象（麦克风用完后触屏失效、完整会话结束才卡死、要重启车机）吻合。

**本次改动**（commit `9493a28`，versionCode 20035）：
1. `SessionController`：触摸事件交给**有界单线程** `touchDispatch`
   （ThreadPoolExecutor 1/1 + ArrayBlockingQueue(64)，拒绝即丢并计数）；
   处理函数只回"已入队"，车机立刻拿到 200。
2. 拆除时的 ACTION_CANCEL、`air.screenOwnership` 收回屏幕时的 CANCEL 都**排进同一个队列**，
   避免"CANCEL 先发、queued MOVE 后到"把宿主按死一根手指。
   顺带去掉 `screenOwnership` 里"宿主不接受 CANCEL 就拒绝 changeModes"的门——
   那等于在事件读线程 + commandLock 上做同步 Binder。
3. 三个**静默丢弃点**各留一条一次性证据：`phoneHasScreen=false`、`geometry==null`、
   队列满；再加一条 `touch injection: first sample delivered to the host`。
   下次真车日志就能分清"车机没发"和"发了我们丢了"。
4. `AirSession.hidSendReport`：触摸报告限流（头 8 条原样 + 每 2 s 一条带计数），
   按键报告不节流。理由：这条处理链在**必须应答车机**的线程上，
   而 `BridgeStore.log` 是 `@Synchronized` + 两条正则 + 复制 2000 行列表，100 Hz 落盘等于自残。

**没动的地方**：解除/重连那条（NO_SYN）这次没碰。最新证据（20033 尾部 `eba382b7`）显示
`RFCOMM selected initiator=phone; peer matched` —— **蓝牙 RFCOMM 是连上的**，
是 iAP 层车机不回 SYN。所以"SDP 缓存通道号过期"这个假设**可以划掉**，
`refreshSdpBeforeConnect` 留着当判别器即可，它不是解法。

### 下一步实验（零成本，区分「状态锁」还是「单向闩锁」）

在导航态下，**在手机上退出导航**（不重连、不重启），看触摸是否自己回来：
- 自己回来 → 车机在跟随某个导航状态信号，找到它就能撬动
- 不回来 → 单向闩锁，只有重启车机能解，协议层无解

### 导航闩锁确认：退出导航不解锁（会话 `4df209d1`）

### 现在的完整模型（三相）

| 状态 | 触摸 | 画面 | 解除方式 |
|---|---|---|---|
| 正常会话 | 有 | 有 | — |
| 导航中 | **无** | 有 | 退出导航**不行**；重连若导航仍在也**不行** |
| 导航结束 + 重连 | 有 | 有 | 重连即可（22:10 与 22:16 两次实测触摸都恢复了） |

所以不是"重启车机才能清"，而是**只要导航还在跑就锁着**；导航一结束、重连一次就恢复。

### 车机侧学习路径的结论

导航那一刻入向流量只有 touch 报告，没有别的；我们也没把 `mix_notify_start_navi` 转给车机，

## ★★★ 触屏失效的根因找到了（会话 `2f8114ca`，23:16，真车单变量验证）

**导航语音（category 2）在会话中途的那次 SETUP，就是车机收走输入焦点的操作。**

### 验证方式（这次基线是核实过的）

同一次装包、同一台车、同一会话内对比：

| 条件 | 导航开始后触摸 | 证据 |
|---|---|---|
| 拦掉 cat2 的 SETUP（`navAudio=false`） | **全程正常** | 97 条报告，跨度 15:15:31 → 15:17:12（导航在 15:16:10） |
| 不拦（之前所有轮次） | 立刻归零，退出导航也不恢复 | 12:19 / 12:33 / 14:22 / 14:32 / 14:49 五次一致 |

日志里开关生效的直接证据：`15:16:10.037` 起不断出现
`Audio category=2 dropped by navAudio=false; no SETUP attempted`，导航动作在 `.293`。

### 精确时序（每个会话都一样，音频永远在导航动作之前）

```
最后一条触摸（点"开始导航"那一下）
+0.0s  host-wakeup-audio-state
+0.1s  cat2 要流 → 100/alert 400 → 回退 101/default → 激活失败
+0.2s  mix_notify_start_navi
之后   0 条触摸
```

### 机制

车机为语音流让出输入焦点后**永不归还**。这和历史上小爱（cat3）那个坑是同一个机制
（`speechAltPcm` 的注释里就写着"用完小爱之后触屏失效，只有重启车机能恢复"），
当初的修法是让 cat3 别去抢 type 100；而 cat2 一直在会话中途做同一件事，所以每开导航必死。

⇒ 之前所有"重新武装输入"的尝试（20037 重发 hidSetInputMode、重建屏幕流、枚举 hidInputMode）
全部打在空处：不是车机"不认"，是我们自己把焦点送出去了。

### 已落地的修法（`34f5f18`，20045）

结构性约束，不是默认值：**category 2 只允许在会话建立阶段预热（`prime=true`），
中途需求一律丢弃**。预热是安全的 —— 15:15:23 那次 SETUP 被接受后触摸照常。
丢弃日志限流到 5 秒一行（导航 PCM 回调约 12 次/秒，不限流会把 1MB 日志冲掉）。

### 顺带查清的导航没声音

cat2 源是 **16000 Hz 单声道**，我们按 `AAC_ELD 48000/2` 建流 →
`Compressed audio category=2 failed: IllegalArgumentException ELD resilience/SBR configuration unsupported`。
所以"导航声从来没有"是必然。下一步：复用会话建立时那条预热流（**绝不能再中途 SETUP**），
并修正 ELD 配置。

## 导航音频 + 重连（`f186675` / `c9a...`，20046 起）

### 导航没声音的真正原因（不是车机）

真车日志 `3834a0f2` / `8669f557` 把两条事实摆在一起：

```
12:17:03.921  Audio SETUP accepted category=2 type=100 dataPort=50122   ← 车机接受了
12:17:03.973  category=2 failed: ELD resilience/SBR configuration unsupported  ← 9ms 后我们自己弄死
12:19:38.335  Audio route refused category=2 type=100/alert status=400
12:19:38.339  category=2 unavailable: Audio stream type=101/default already has a session
```

- 预热时 `100/alert` 是**被接受**的，死在我们的 AAC-ELD 配置校验上（源 16k/1，广告只有 ELD 48k/2）。
- 导航真开始时 `type 100` 已被主音频占住 → 400；兜底的 `101/default` 又被 **category 3 的预热流**占着，
  而那条流整场 **发 0 个包**（心跳恒 `c3=0/-`，`Audio host callback category=3` 一次都没有）。
  小爱的声音其实是从 category 1 媒体流出声的。

### 修法（不建任何中途 SETUP）

1. `pcmAlert` 默认 **true**：cat2 走 `101/default` 裸 PCM 48k/2，完全不碰编码器。
2. `bootstrapPlayback` 顺序改成 **2→1**，category 3 不再预热（它只占位不发声）。
3. 中途来的 cat2 PCM 不再被吞掉：`audio.testFormat(2)!=null` 时 `return false`，
   落到 `HostAudioBridge.receive()` → `Pcm16Converter`（16k/1→48k/2 重采样+上混）→ 已建好的那条流。
   **一条新流都不建，车机的输入焦点不会被拿走，触屏修复不回退。**

### 重连不上：已经抓到的现场

重装 APK 打断了活会话，正好复现：每一次尝试都是
`RFCOMM peer matched`（蓝牙通）→ `stage DETECT` → `iAP NO_SYN: no peer SYN within 7000ms`。
即**车机仍然占着上一个 AirPlay 会话**，不肯开新的 iAP 会话。

- 上一次会话（15:28:05）也是这么失败的，从 15:25:39 起连挂 5 次，**约 2.5 分钟后自己连上了**
  → 车机有释放定时器，用户以为"必须重启车机"，多半是没等够。
- 代码里原有的 `refreshSdpAfterNoSyn` 从来没生效过：`startSession` 失败后 `stopSelf()`，

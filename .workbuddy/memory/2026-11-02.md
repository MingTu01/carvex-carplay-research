## PT 改动的教训（已撤回）

## 22:30 音频无声的根因：线上 PT 用错了（commit 52732e4，APK 20022）

- **结论**：音乐流（category=1，SETUP raw type=102）一直把 102 直接当 RTP 的 PT 发。
  `spec/01-audio-streams.md` **R-1.1 是 MUST NOT**：SETUP 的 raw type 与 RTP 的 PT 是
  两套编号，禁止互换；唯一已知二次映射是 `raw102 → gen(96)`（A01.5）。接收准入掩码
  `0x3d13`（R-1.2，pt ∈ {96,97,100,104,106,107,108,109}）里**根本没有 102**。
  → 车机在**入口处就丢包**：SETUP 200、包在发、日志全绿、全程无声，
  **连明文诊断也无声**（准入检查在任何密码学之前）。
- **两次走错都没有真车证据**：① 初版恒等映射引的是 `X-0029`，research/ 里根本不存在；

## 23:25 — 声音无声的根因：帧密码选错族（raw102 该用 AES-CBC-frame，不是 CTR）

20022 实测 `wirePT=96` 已生效（PT 假设排除），但**仍然全程无声**。重新翻
FairPlay 的分派表后找到根因。

**关键证据**：`research/protocol/airplay_fairplay_crypto/analysis/14` **A-44**
（`0x2519bca6c..bd120`，36 个原指令锚点，C14 `verify_cryptor_dispatch.py`），
type/G 分派表在 **G=0** 下：

| type | G=0 | G≠0 |
|---|---|---|
| 96/102/103 | **A=CBCFrame** | ChaCha(flag=1) |
| 100/101/106/107 | **不建密码器** | ChaCha |
| 110/111（屏幕） | **A=CTR** | ChaCha(flag=0) |

**为什么这张表可信（不是猜）**：视频是 MainScreen/AltScreen（110/111），
我们用 CTR 就出画面 → 而表里 110/111 只在 G=0 给 CTR → **本会话 G=0 成立** →
那么 MainHighAudio(102) 就必须走 CBCFrame。同一张表把"视频为什么通、音频为什么哑"
一次解释干净，互为印证。

- **旧代码**：`Mfi.streamCipher(id)` 只造 AES-CTR，音频视频共用一条。CTR 是屏幕流的
  帧密码，不是 102 的。表现就是包在发、日志全绿、车机还回过重传请求，但喇叭哑。
- **密钥材料不用动**：A-46（`0x251aa97a0`/`0x251aa9a60`）的 Sender Legacy KDF
  `SHA512(name‖dec(id)‖masterKey16)[0:16]` 视频音频同源，A-45 说 CBC 方法收的正是
  key/iv 两个 16B 出参，A-42/R-6.5 又说固定 128 位。**换的只有帧密码这一族。**
- **CBCFrame 帧语义**（A-40 `0x18be62ba4`）：`full=len&~15`，每次调用用**保存的初始 IV
  重置**、整块 CBC、尾部 `len%16` 原样直通。**不是**链接上一包末密文块，**不是** PKCS#7。
  和 CTR 的"计数器跨包连续"正好相反 —— 测试里两条都钉了。

## 23:50 — CBC-frame 实测 FAIL；断连重启车机的根因找到并修了

### 声音：c62ad08 的 CBC-frame **没修好**（假设 FAIL）
日志实锤 `Audio crypto category=1 mode=AES-CBC-frame(MFi/SAP)`，包正常发
（46.9 pkt/s，正好 48000/1024），SETUP 200，仍然无声。

**两种帧密码（CTR、CBC-frame）都不出声 ⇒ 问题不在密码学。** 这条否定结论
本身很有价值：候选从"密码族"收敛到两条路共用的东西。

已逐项排除：wire PT（96 实测生效）、帧密码族、audioFormat=0x800000、
时间戳语义、音量、传输、包速率。**KDF 也基本排除**——A-18 明确"屏幕/流密钥
同样走 AirPlayStreamKey/IV + 索引，与 Legacy 完全同名同构，一个实现共用一份 KDF"，
视频用同一套就出画面。

剩下的候选（下一次各单独验证）：
1. **载荷封装 ADTS vs raw AU** —— 两条路共用，解码器拿到错形状就是全程哑。
   编码器产 csd-0（AudioSpecificConfig）说明本端是 raw AU 模式。
2. **PT 96 在 maxPackets>1 时会被当 RED 解析**（spec01 R-1.9 / rtp_timing spec09
   R-9.2：`PT==0x60 且合并模式` 就有元素区，正文起点变成 `buf+12+(4C-3)`）。
   若车机的合并数>1，我们的 AAC 字节会被当元素扫，解码器拿到错偏移。
   `analysis/01` 的 PT 表也写：96「仅 maxPackets>1 时按 RED 解析」，
   而媒体音（music）在同表是 **PT 100 `main`**。`raw102→gen(96)` 只是 **INFERRED**，
   已经实测两次不出声。
3. **102 缺失的 output control transport** —— `AudioSetupDescription` KDoc 自己记着；
   车机对 type=102 回 **controlPort=47978 + dataPort=37596**，对 100/101 只回 dataPort。
   我们把 controlPort 只喂给麦克风（`microphone?.updateControlPort`），媒体路上**丢弃**。
   `Audio clock` 也写着 "receiver playback clock/flush not established"。
4. `audioPlaintext` 逃生阀还在（设置里可切，不用重打包），用于判定"车机压根没装解密器"
   —— R-9.4：`obj+0xa0` 为空时直接放行明文返回 0。features 里有
   `AUDIO_AES_128_MFI_SAP_V1`，所以这条可能性不高，但它免费、5 秒能验。

另：本端新增**音频首包诊断**（只打一次）：`Audio first packet ... wirePT= bytes= head=<hex>`，
把实际发出的线上字节钉进日志。研究侧 OPEN-RUNTIME-1 一直缺的就是这个。

### 断连要重启车机：根因找到，已修（commit `2ea91e3`，APK 20024）
`RtspClient.stopSession` 发的是 `Plist.encode(emptyMap())` —— body 里**既没有
streams 也没有 teardownType**。日志里那句 `teardownType=absent` 就是它。

固件依据（spec07 **R-7.6** / analysis07 **TD-05**）：整会话收尾必须发
**不带 streams 的 `tdwn`，并带 `teardownType=2`**，且"控制连接先断会导致 tdwn 发不出去"。
车机收不到这个标记就把旧会话状态留着，下次连接被挡掉 → 只能重启。
顺序本来就对（先注销本地流 → TEARDOWN → 最后关控制连接），缺的只是这个字段。
单流 teardown 的 teardownType 仍是条件字段（R-7.1），不一起改。

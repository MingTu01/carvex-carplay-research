# 2026-11-07 启动页换成视频 + 版本命名 + "一个包兼容全部品牌"的答案

## 1. 启动页视频

用户给了 `C:\Users\Administrator\Downloads\logo.mp4`，要求把「开机连接车机后显示的那张图」
换成视频。那张图是 `LocalVideoDisplay.kt` 的 `LocalVideoPhase.SPLASH` →
`BrandPage(brand,"正在建立投屏通道")`：品牌名 + 一行字 + 三张捐赠码。

片源实测（没有 ffprobe，自己解 MP4 box 拿到的）：1280x720、10.08 秒、H.264 **High
profile level 3.1**、AAC 立体声、1.6MB。`stsd` 里的 `avcC` 直接读出 profile=100 level=31。

改动要点：

- 拷成 `app/src/main/assets/splash.mp4`，包里是 **Stored（未压缩）**，AGP 本来就对 mp4 不压缩。
- **TextureView，不是 SurfaceView**：这块画面画进 VirtualDisplay、输出面就是编码器输入。
  SurfaceView 自开合成层，走私有显示经常整块黑且无异常；TextureView 走普通视图合成。
- 静音（`setVolume(0f,0f)`）：片源有 AAC 轨，但车机开机画面不该响。
- **失败一律退回品牌页**，不抛：缺资源、MediaPlayer 报错、显示被拒都走 fallback。
- 先拷到 cache 再 `setDataSource(path)`，不用 `openFd`——`openFd` 只对未压缩资产成立，
  而"资产是否被压缩"是打包细节，出问题只会表现为**车上黑屏**。cache 文件名带 VERSION_CODE。
- 加了 `SplashVideoSurfaceTest`：拿 ImageReader 顶替编码器 surface，读帧断言有非黑像素。

### 踩到的坑

**MIUI 拦测试包安装**：`:app:connectedXiaomiDebugAndroidTest` 报
`INSTALL_FAILED_USER_RESTRICTED: Install canceled by user`。主包能装是因为覆盖安装，
测试包是新包名 `com.baidu.carlife.xiaomi.test` 就被拦。所以那条 instrumentation 测试
**一次都没跑过**，别在汇报里说成已验证。

## 2. 版本命名

`20072` → `1.0.73`。规则改成 `<主>.<次>.<提交数>`：

```kotlin
val versionMajor = 1
val versionMinor = 0
val releaseVersionName = "$versionMajor.$versionMinor."+(gitCommitCount ?: 1)
```

`versionCode` 不动（仍是 20000+提交数），升级顺序不变。手写的只有主/次两个常量。
`android/AGENT.md`、`AGENT.en.md`、`README.md` 三处规则同步改了（§9 要求中英同步）。
实测装到手机上：`versionCode=20073 versionName=1.0.73`。

## 3. "一个包能完整兼容小米之外的品牌吗"

- 5 个 flavor 的差别**只有** `applicationId`（`com.baidu.carlife.<brand>`）和一个

  **honor 的 hostServiceClasses 是空集**，AGENT.md 也写了"仅打包；宿主插件不可用"。
  所以不是"5 家适配"，是 4 家声明 + 1 家占位。
- 拉下 `com.miui.carlink` 的 base.apk（56MB）grep：**没有 `com.baidu.carlife.*` 字面量**，
  只有资源名 `baidu_carlife` 和大量 `CarLife` 文案。说明 CarWith 不是靠硬编码包名找我们
  （真实方向是我们绑它的 `com.xiaomi.ucar.carlife.CarlifeConnService`）。
  但**它是否校验调用方包名/签名，要读它的服务实现**，没到那一步。

结论口径：代码上一个包能覆盖（alias 已齐，brand 从单值换成按宿主包名匹配即可）；
真正的未知是 `applicationId` 只可能有一个，而每个品牌对应一个不同的
`com.baidu.carlife.<brand>`。按 AGENT.md，改 applicationId 属兼容性变更、必须有证据，
而除了小米这台，其他四家既没有设备也没有服务端证据 → 对它们保持 OPEN。

## 4. 车机没声音的真因 + 默认值陷阱（1.0.76）

用户反馈"视频没问题，但是声音好像没有了"，经澄清是**车机里音乐/导航没声**，不是启动视频。

**根因**：`Options.audioEnabled` 默认 `false`，而 `AirSession.kt:1170` 在它为 false 时
不是"跳过测声音"，而是 **`throw UnsupportedOperationException`** —— 整条 MFi/SAP 音频流
从未开始。`audioEnabled` 的注释本身就写着"旧结论已被推翻，现在只是这一版要不要测声音"，
是上游遗留的诊断开关，被当成了功能开关。

**这个 bug 真正的教训（值得反复记住）**：光把 `Options` 默认值改成 `true` 是**无效的**。
`options.xml` 里早已落了字面量 `audioEnabled=false`，默认值只对新装生效。已安装用户升级后
依然是关的，而这次改动又把 UI 开关删了 → 他们会升级成一个**没声音且无处可开**的版本。
所以必须配一次性迁移：`DefaultOnSettingsMigration`，用 `defaultsRevision` 标记位做闸门，
`audioEnabled` 与 `experiment` 各提升一次，已到版本号就直接 return（幂等，且不覆盖用户
事后用 run-as 手改的值）。

设备实测 `options.xml`：`experiment=true`（本来就开）、`audioEnabled=false`、
`frontSurface=false`、`audioPlaintext=false`、`audioRawWirePt=false`。

**同时清掉的 UI**（用户："静帧重发这些测试按钮都可以去掉了"）：
`SettingsPage` 里实验认证、静帧重发、音频投送、音频明文四个 `SwitchRow` + 说明文字，
以及孤立的 `airplay_security_automatic` 标签（一直没配开关）。三语 `strings.xml` 里 9 条
字符串一并删除。`Models.Settings` 四个字段与 `DeviceViewModel` 四个 `update*` 方法随之删除；
`Options` 里的字段**保留**（要落盘、要能广播/run-as 改），只是不再经过 UI 状态。

启动视频顺手把 AAC 轨去掉：把 `soun` trak 换成等长 `free` box，`mdat` 绝对偏移不变
（9450），所有 `stco` 依然有效。音量本来就是 0，但一条活着的 AudioTrack 平台仍会混音/duck，
开机画面没理由占一条。

版本 `1.0.76` / `versionCode 20076`，AC92 校验 APK 内 `assets/splash.mp4` 与源文件 md5 一致
（`8183c7711e74e2d76156be4fe6daf19c`），条目 `Stored`。
**提交只在本机，没推上游**（用户明确：自己用的东西不提交给原作者）。

## 5. 车机没声音的真正根因：启动视频抢跑（1.0.77）

**先记教训**：我一度怀疑是 CarWith（`com.miui.carlink`）的音频路由设置/`audio diversion` 开关，
甚至准备去改系统设置。用户直接叫停：「不要去看 carwith 里面的内容……他就是原生的，后续升级也不影响」。
这条要长期记住：**宿主是原生的、不受我们控制、也不该去改**。找不到原因时不要往它身上赖。

### 证据链（1.0.76 实车，2026-11-07 19:12，会话 9c40237f）

```
36.576 NuPlayerDriver reset / initiating video decoder shutdown   ← 启动视频刚拆
36.615 CarlifeConnService: prepareCast                            ← 39ms 后宿主接管画面
36.699 CarlifeAudio: try to start music record
36.700 AudioSource-java: audio channel close                      ← 宿主抢不到音频输入，直接放弃
```

之后整场 `hb ... audio[c1=0/-,c2=0/-]`，我们这边 **所有 SETUP 都是 200**
（cat2 `101/default` accepted、cat1 `100/media` accepted、`MainAudio owner=ours`、`RECORD repeat 200`、
`volume 0dB accepted`）。**握手全通、通道全空**。

对照：`local-backups/logs/diag-2006*.log` 里没有启动视频的那几个包，
`audio[c1=]` 分别是 20068 / 3896 / 125912 / 162584 / 119089 / 64022 / 91383 —— **全都在发**。
1.0.75 加视频 → 哑；1.0.73 没视频 → 有声。三个数据点同向。

### 机制

`LocalDisplay.close()` 只 `await` 了 `window.dismiss()`，而 `MediaPlayer.release()` 挂在
`SplashPage` 的 `DisposableEffect{onDispose{...}}` 上，**Compose 异步执行**。
所以 `close()` 返回时解码器还在 shutdown，紧接着 `prepareCast` + 宿主 `AudioRecord` 就撞上，
宿主 `audio channel close` 一次之后再没重试（线程 23101 之后还在处理命令，只是不再录音）。

### 修法（1.0.77）

- `SplashVideo` 维护活跃播放器登记表，`releaseActiveNow()` 在 `close()` 里、主线程上**同步**释放；
  `close()` 返回即代表解码器真放手。
- `release()` 顺序改为 **先 `setSurface(null)` 再 reset/release**。
- `HostAudioBridge` 加自证：建流 5 秒内 `received==0` 就打
  `Audio host delivered no PCM within 5s ... the gap is on the source side, not in RTP`，
  省掉下次翻 56MB logcat。

### 副产品：如何确认宿主到底有没有送数据

`SessionController` 的 `HostCallbacks.pcm()` 一旦被调必打 `Audio host callback category=... phase=first-format`；
`HostAudioBridge.receive()` 必打 `Audio source first category=...`。
**这两条为零 = 宿主没送，不是我们丢包**。别再去看 `audio[c1=]` 猜。

启动视频同时换成 `C:\Users\Administrator\Desktop\logo2.mp4`（同参数 1280x720/10.08s/H.264+AAC，
仍用「把 `soun` trak 换成等长 `free` box」的办法去音轨，`mdat` 偏移 9450 不变）。

版本 `1.0.77` / `20077`，md5 `9ff60e01be7b8c5d89cf9cf4cee5d263`。

## 6. 声音已解决，转卡顿：自适应静帧补发（1.0.78）

### 先定性的那句结论

用户重置 CarWith 设置后声音正常了 —— 所以第 5 节那套「启动视频抢音频通道」的推断
**被实车证伪**：1.0.77 日志里 `onSetVideoSurface(0x0)` 到 `video shutdown completed` 只花了 11ms，
22ms 之后才 `prepareCast`，宿主仍然关通道。真凶是 CarWith 自己的设置，不是我们的释放时机。

`releaseActiveNow()` 那套改动仍然保留 —— 它不影响任何东西，且「close() 返回即解码器放手」
本来就是对的时序。

### 卡顿的两条独立成因

**音频侧（能听到的）**：CarWith 的「音频融合」在导航播报时把音乐通道停掉。
实测 `11:33:52.778 category=1 pause` → `11:34:04.528 category=1 resume`，**停了 11.7 秒**。
这是车机行为，我们这边只负责不插静音（`HostAudioBridge.state()` 里注释写清了）。

**画面侧（这次要改的）**：画面一停，视频时间戳也停；音频时间戳还在走。
恢复时接收端面对攒下来的 A/V 偏差，只能靠丢帧追回来 —— 用户看到的就是「一动先卡一下」。

### 为什么之前没补帧

`Options.frontSurface` 默认 `false`，而 `repeatFrame` 只在「宿主没接管画面」那条分支里赋值。
宿主接管（正常情况）时两条补帧路径**都不存在**，`canRepeat()` 恒为 false，心跳根本不跑。
日志里那句 `front surface disabled, so no P frames while still (latency first)` 就是在说这件事。

### 修法

- `Options.frontSurface` 默认改 **true**：前置画布是静止画面重新进编码器的唯一通道。
- `VideoIdleHeartbeat` 加 `stillAfterMs`（默认等于 `intervalMs`，向后兼容）：
  **第一帧补发看静止阈值，之后按 interval 续命**。`250ms` 的 tick 让 500ms 阈值真的能落地。
- 早到容差从 `intervalMs*3/4` 改成显式的 `earlyToleranceMs=50` —— 原来那个 3/4 是为了容忍
  一秒定时器的抖动，tick 变细之后它会悄悄把节奏压成 750ms。
- `DefaultOnSettingsMigration` 改成**按修订号分步**（`steps` 列表，下标+1 即修订号）：
  已经跑过第 1 步的设备（`defaultsRevision=1`）如果只加键不加步，会被闸门永久挡在门外。

### 数据（下次实车对照用）

- 视频 TCP，`bitrate=2396160`，~10KB/帧 @30fps
- 音频 UDP，`framesPerPacket = rate/200` → 48000 下 240 帧 = **960 字节负载**，
  200 包/s，1.54Mbps。**远小于 MTU，不会被 IP 分片**
- CarWith 的 AudioRecord 是 `r_submix` 上 **44100/2ch/PCM16**（`openInputStream` 那行），
  我们转发时 44.1k→48k 重采样

### 实机确认（1.0.78 / 20078）

- 首次启动 logcat：`CarVex: defaults migration applied: promoted switches are now on (revision=2)`
- 二次启动无此行 → 幂等成立
- 顺手补了这条 logcat：release 包 `run-as` 进不去，看不到盘上的值，
  上次排查就是这样断了证据链
- APK `9c9d050f1891a9567988227323b03829`，已装到 cd8a3355

## 7. 小爱没声音：语音通道和导航抢同一条路（1.0.80）

### 现场证据（session d8b32229，1.0.79 的 logcat）

1.0.79 加的 `CarVexAudio` logcat 镜像第一次用上，当场抓到：

```
21:35:06.341  Audio bootstrap plan=cat=2 type=101/default codec=PCM16, cat=1 type=100/media
21:35:14.252  Audio category=3 PCM 16000 Hz channels=1 playback matches=3
21:35:14.253  Audio category=3 selected type=101/default codec=PCM16/48000/2
21:35:14.255  CarPlay audio category=3 unavailable; other streams retained:
              IllegalStateException  Audio stream type=101/default already has a session
21:35:14.376  Audio source category=3 has no established stream ... dropped here and never reaches RTP
```

### 根因

CarWith **只广告了一条非音乐路由**：`101/default`。会话建立时它给了导航（cat 2）。
语音（cat 3）首选 `100/speechRecognition` 没被广告，于是回退到 `speechAlternate = 101/default`
—— 和导航**完全同一个 (type, purpose)**，被 `AudioStreamLifecycle.reserve` 自己的占位检查拒掉。
所以语音流从来没建起来，小爱的 16k/1 PCM 全部落进 dropped。UI 正常、就是不出声。

**注意**：这不是"我们没实现语音"，是**两条流抢同一条路**。原来的代码里没有任何一条
"选不到路怎么办"的退路。

### 修法

`HostAudioBridge.routeFor(category)`：某一类没有自己的流时，把它的 PCM **并进活着的
那条非音乐流**（先 2 后 1）。理由 —— `101/default` 本来就是接收端给"非音乐音源"准备的
那一块地方，语音要是能建流，拿到的也是它。所以并进去路由/格式/解码路径全一样，
却不需要任何 SETUP，也就不碰车机的输入焦点。

- 有自己的流时**绝不合并**（车机真广告了 `100/speechRecognition` 就各走各的）
- `Block` 加了 `source` 字段：日志里要能分清"这段声音本来是哪一类送来的"
- 两条行为都有单测：`speechWithoutItsOwnRouteIsMergedIntoTheLiveLane`、
  `aCategoryWithItsOwnRouteIsNotMerged`

### 副作用与未知

- 语音和导航现在共用一条流。两者同时出声会交错 —— 但小爱说话时音乐/导航会被 duck，
  实际不容易撞上。
- 每条流内的 `Pcm16Converter` 会在 16k/1 与 48k/2 之间来回重建。块级切换代价可忽略。
- **未验证**：小爱说话时车机上到底能不能听见。要等下一次实车。

版本 `1.0.80` / `20080`，md5 `69d90c44f8f7460f1e7814b1268b2df4`。

## 8. 画面糊的根因：画布停在 1024x600，车机建议全被宽高比判掉

用户反馈两点：语音和导航能不能**真正分开**；画面**有点模糊**，车机是 1280x720、
投屏设置里默认 1920x1080，但**改哪个都没区别**。

### 糊的原因（数据已坐实）

logcat 里 `Local display: virtual display created id=528 state=2 1024x600 density=170`
—— 实际渲染的画布是 **1024x600**，既不是 1280x720 也不是 1920x1080。
600p 被面板放大到 720p（1.2 倍双线性）必然糊，文字尤其明显。

为什么停在 1024x600：

| 来源 | 值 |
|---|---|
| 接收端 `/info` 自报显示 | 1024x600 |
| 车机 `carlife_encode_format` 查询建议 | 1280x720 / 1920x1080 |

老代码的采纳判据是 `proportional = rw*qh == rh*qw`（**整数完全相等**）。
1024x600 vs 1280x720 差 **4.2%** → 判据为 false → 整条建议作废 → 永远回落 1024x600。
所以"改分辨率没反应"不是 CarWith 的锅，是我们自己把它拒了。

码率账也对得上：`1024*600*30*13/100 = 2,396,160`，与日志 `bitrate=2396160` 一致
（`nominalBitrate` 公式 `w*h*fps*13/100`，每像素每帧 0.13 bit）。

### 改法

- `SessionController`：采纳判据改成**相对误差 ≤6% 且不缩小**。
  缩小纯粹丢细节；放大由码率同比例补齐。
- **`ProjectionGeometry` 里还藏着同一个整数判据**（`require` 会让 1280x720 直接抛异常）。
  两处统一到 `ProjectionGeometry.ASPECT_TOLERANCE_PERCENT=6` +
  `ProjectionGeometry.aspectErrorPercent(...)`，一个数只有一个出处。
  触摸映射按轴线性归一化 —— 和接收端把画布铺满自己屏是同一个映射。
- `nominalBitrate` 上限 12 Mbps（与 `VideoRatePolicy` 天花板一致；再高只是换成排队延迟）。

### "两个音频能不能分开"

**物理上不能。** CarWith 只广告一条非音乐路由 `101/default`，`(type, purpose)` 在接收端
就是一条流，两个 send 混着发只会两边都听不清。能做的是**让路**而不是混音：

- `claimLane(route, source)`：一次只有一个来源占通道
- 换人需要 400ms 静默（`LANE_HOLD_NS`），避免在同一句话的块间隙里来回换
- 优先级 3（语音）> 2（导航），语音可**立刻抢占**：被截断的回答就永久没了，
  导航播报几秒后还会重播
- `Snapshot.yielded` 记账

效果接近"分开"（不会同时说话），但确实不是两条流。

### 测试踩坑

两条共享通道用例的**期望字节数是错的**，不是逻辑错：
- 语音 1920B(16k/1) → 48k/2 实际 **11512**，不是理论 11520（重采样器带相位状态，少 2 帧）
- 导航 5760B(48k/2) → 48k/2 **原样透传 5760**，不是 23040（`source==target` 直接返回）
- 教训：涉及重采样输出的断言**一律用同一套 `Pcm16Converter` 现算期望值**，不写死。

版本 `1.0.81` / `20081`（提交 81）。

## 9. 用户纠正 + 1.0.82（诊断面板 / 启动素材上传 / 画质档位 / 三路音频开关）

### 被用户纠正的一处

我上一轮断言"CarWith 只广告一条非音乐路由，物理上分不开"—— **错了**。
用户：CarWith 的音频就是三路（媒体 / 小爱 / 导航），音量可以分别设置。

实车日志反证：`Audio category=1 route check: type102 advertised=1 encodable=1`。
**type102 是广告了的**，我们从来没用过。老的 `CarPlayAudioPlan.media = Route(1,102,"media")`
一直因为 `preferPcm` 的短路（`pcmRoutes` 先跑）落在 `100/media`，102 从没被试过。

教训：`/info` 里的每一路都要摊开看，不能只看"哪一路建成功了"。

### 1.0.82 做了什么

1. **诊断面板**（`ui/component/Diagnostics.kt`，挂在 DeviceInfoPage）
   - 车机自报显示 / CarWith 建议 / 实际编码画布 / 编码器 / 码率 / 是否发生缩放
   - 三行音频（媒体/导航/语音）：各自落在哪个 `type/purpose`、SETUP 成没成、发了多少包
   - 车机广告的**全部**音频路由（type/purpose + 可收格式），这是"能不能分三路"的唯一依据
   - 数据全部由会话层回填（`SessionState` 的 diag 字段），不解析日志文本
2. **启动素材上传**：设置里可选视频/图片（≤5MB），复制进 `filesDir/splash/`。
   必须在私有目录：SAF 的 URI 授权只活当次进程，直接引用会在下次连接时静默失效。
   图片走 `BitmapFactory` + `ContentScale.Fit`，视频仍用 MediaPlayer。
3. **画质档位**：`VIDEO_QUALITY_BITS_PER_HUNDRED = [13,20,30]`，默认 1（0.20 bit/px）。
   720p30 → 3.59 / 5.53 / 8.29 Mbps。
4. **三路音频分离开关**（默认关）：媒体改走 102，把 type100 让给语音。
   - 关闭时行为与 1.0.81 逐字节相同
   - 102 上没有可用编码 → 自动回退 `100/media` PCM（有回归用例钉住）
   - 语音自己的 100 被 400 → 回退 101/default（"分不开但有声"）

### 踩坑

- `ProjectionGeometry` 的 `require` 里藏着同一个整数宽高比判据，采纳 1280x720 会直接抛异常。
  已与 SessionController 统一到 `ASPECT_TOLERANCE_PERCENT=6`。
- `selectPlayback` 的 `outputOnly`（免 duplex）只对 `pcmRoutes` 快路径生效，choices 循环里没有。
  所以分离模式下语音退回 `101/default` 必须在 `pcmRoutes` 里两个落点都留着，否则 requireDuplex
  会让它直接变 null。
- 包名是 `com.baidu.carlife.xiaomi`（伪装成 CarLife host），不是 `io.github.iamr0s.carvex`。
  `pm list packages | grep carvex` 查不到。

## 10. 1.0.83：媒体必须用 PCM，压缩编码在 CarWith 上等于"要不到数据"

### 1.0.82 的分离开关其实生效了

用户说"没起作用"，但日志里三条流全部 SETUP 200，而且落在三个不同的 type 上：

```
22:54:09  Audio bootstrap plan=cat=2 type=101/default PCM16,cat=1 type=102/media AAC_LC
22:54:09  Audio SETUP accepted category=2 type=101
22:54:09  Audio SETUP accepted category=1 type=102
22:54:26  Audio SETUP accepted category=3 type=100
22:54:26  Audio actor=category=3 blocks=82 bytes=314880  ← 小爱有独立流了
```

**但是 category=1 整场一个 `Audio host category=1` 都没有** —— 媒体没源。

### 根因：CarWith 只采 PCM

```
22:54:09.386  CarlifeAudio: try to start music record     ← 它确实启动了
22:54:09.722  CarlifeAudioController: start create tts / vr record
```

music record 起来了，但我们给它注册的是 `AAC_LC` 流，它编码不了就不推。SETUP 200 +
空 RTP 路径，和"正常工作"在日志上一模一样，只有数包才看得出来。

**教训**：`SETUP accepted` 只证明注册成功，不证明有源。以后判音频好坏先看包数。

### 改法

- `pcmOnMedia102()`：分离模式下 102 优先走 **PCM**。
- 102 没有 PCM 位时**完全不选它**（`skipped += media`），落回 100 的 PCM。
  压缩编码在 102 上等于一条永远没有源的流，选中就是音乐变哑。
- 这个例外只写在一个窄函数里，**没有**放宽 `wireSupported`。放宽会连带改掉默认路径，
  而且旧车机结论（PCM 只覆盖 100/101）是实测来的，不能为一个实验推翻。
- 诊断面板挪到**设置页顶部**（原来在设备详情页，设备没列出来就进不去 = 看不见）。
- 同一份数据镜像到 logcat `CarVexDiag`，5 秒一条（video 一行 + lane/route 各一行）。

### 测试

`SeparatedAudioLanesTest` 扩到 6 条，其中三条是护栏：
- 关掉开关时媒体仍在 100 用 PCM，且不依赖本机编码器
- 102 只有压缩编码 → 必须落回 100
- 语音被 400 → 落 101/default（"分不开但有声"）

版本 `1.0.83` / `20083`，md5 `60ac1093f14b7fadcda8efaba7da6015`。

## 触屏失效真正修法（1.0.86）

- 根因不是"用错路由"，是**会话中途发起 SETUP 这个动作**本身：车机让出输入焦点后永不归还。
  1.0.83 走 100/speechRecognition、1.0.85 走 101/compatibility，目标不同、都回 400、触屏都没了。
- 漏网的正是 category 3 的两处：`startAudio`（小爱出声）与 `startSpeech`（车机发语音动作）。
- 修法：`requestAudio` 里 `if(!prime)` 一律不建流，能并就并进活着的通道，否则丢弃；`startSpeech` 置空。
- 三路分离关闭：这个接收端只有 100/media 与 101/default 两个 PCM 位置，101/compatibility 实测 400。
  设置页移除「三路音频分离」「会话诊断」「通知使用权」。

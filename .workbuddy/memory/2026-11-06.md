# 2026-11-06 车机断电重启的根因（第二次排查，这次定案）

## 结论：不是我们发了什么，是我们**少发**了什么 —— TEARDOWN 一次都没成功过

全量统计（所有归档 + 当轮日志）：

| 项 | 次数 |
|---|---|
| 发送 `TEARDOWN`（77 字节，整会话结束通知） | 4 |
| 收到车机对 `TEARDOWN` 的应答 | **0** |
| 因 `SocketException` 失败 | 4（全部） |
| 根本没尝试（`teardown skipped: no captured AirSession`） | 22 |
| 车机回 `5703` | 39 |
| 我们发 `5702` | 37 |

那 4 次全部是在"已经发现失败之后"才补发的，socket 早死了。绝大多数情况更糟：
CarWith `forceStopApp` 是 SIGKILL，进程没有任何回调机会，连"要发 TEARDOWN"这行都跑不到。

## 闭环

```
CarWith 杀进程 / 网络断
  → 我们没发出 TEARDOWN
  → 车机留着上一次会话
  → 下次重连，5702 石沉大海（它不拒绝，它直接沉默）
  → 卡在 DETECT（用户看到的"查找车机身份"）
  → 我们每 5 秒重发 5702，共 25 秒预算
  → 车机在"新请求不断来、旧会话放不掉"下自复位（用户看到的"重启"）
  → 重启清空旧会话
  → 手机自动连上，一切正常
```

**用户自己那句「车机重启成功之后手机就会正常自动连接上」就是反证**：重启之所以有用，
正是因为它替我们做了 TEARDOWN。不是重启让网络变好。

顺带解释了"车机需要 40~47 秒才肯接受 iAP"（两次实测都是 45.7 秒）——那很可能不是启动耗时，
是车机自己释放僵死会话的超时。

## 判定依据：成功轮与卡死轮的发包**逐条一致**

`8e44080f`（成功）与 `81617877`（卡死）的 identify 序列完全相同：
`1d00 → 1d01 → 1d02 → aa00 → aa06 → aa00 → aa01 → aa02 → aa03 → aa05 → 4e09/4e0a/4e0e/4e0d/4e0c → 5702`

唯一差别：
- 成功轮 `14:13:04.613 TX 5702` → `.614 RX 5703`（**1 毫秒**）
- 卡死轮 `14:12:29.496 TX 5702` → 永远没有 5703

车机最后一次出声是 `.339` 的 `aa03`。所以**手机发的东西没有问题**。

## 20069 的改动（提交 `40ec2d8`）

1. **`0x5702` 只发一次**，不再每 5 秒重发（预算 25 秒）。
   - 依据：`IapLink` 的 `SILENT_ABORT_MS` 注释早已记录同一件事（2026-11-05 22:07:09
     重传 9 次 → 车机 `Connection reset by peer` → 黑屏重启）。当时只掐掉了 iAP 层每秒一发，
     外层这个 5 秒循环把同样的错误以更粗颗粒重演了一遍。
2. **沉默→`CarHoldsPreviousSessionException`**（继承 IOException，不能是 IllegalStateException，
   否则落进终止性集合）。
   - 两种沉默形态都要接：`PeerSilentException`（3 秒无 ACK，链路还活着）
     与 `iAP ACK timeout seq=N`（链路层重传配额用完，**抛之前已 close 链路**）。
     哪条先到取决于 SYN 协商的 retryMs/retries。
3. **`SessionController` 对它有 45 秒专属退避**（`CAR_RELEASE_BACKOFF_MS`），不是 2 秒。

## 20069 实测验证

安装（22:32:32 打断一个跑了 17 分钟的会话）后：

```
22:32:48.267  iAP frame TX seq=86 csm=5702     ← 唯一一次应用层发送
22:32:49.268  iAP frame TX seq=86 csm=5702     ← 链路层重传（同 seq）
22:32:50.279  failure: CarHoldsPreviousSessionException  ... not acknowledged for 3000ms
22:32:50.587  新一轮（CarWith 重启，2 秒后）
22:33:01.143  再一轮
22:33:44.267  再一轮
22:33:50.498  iAP TX 5702  → 车机接受
22:33:50.509  stage WIFI        ← 之前是卡死在这里之前
22:33:55.491  stage PAIR
22:34:03.045  交给 CarWith，出画
```

- 5702 应用层总发送：**3 次**（2 次被拒、第 3 次成功）。旧行为下每轮最多 6 帧。
- **车机没有重启。** 78 秒后自己放行了。

## 仍未解决的（下一步）

1. **45 秒退避会被 CarWith 的 rebind 绕开**：它 0.3~10 秒就把进程重启，新进程没有记忆。
   要真正生效，得把"刚才被车机拒过"**持久化**（`session.xml`），启动后先等剩余额度。
   `carBusyAt()`/`markCarBusy()`/`KEY_CAR_BUSY_AT` 还在文件里，原本就是为这个留的钩子，
   目前无人读。
2. **SIGKILL 下无法发 TEARDOWN** 是硬限制。唯一可能的解法是持久化会话标识，
   下次启动先结束旧会话——但新连接能否 TEARDOWN 旧会话的 URL，**没验证过**，需要实验。
3. 每晚反复出现"车机重启"→ 说明这台车机对僵死会话没有自愈能力，只有复位。
   所以"少刺激它"比"连得更快"重要一个数量级。

## 方法论教训（我今晚犯的）

- 一开始把"车机重启"当成重连测试，其实它根本不是重连。
- 安静期用错了基准：算的是"我们自己失败之后等 20 秒"，正确基准是"**车机掉电那一刻**"。
  基准错了，所以它只让所有恢复慢 20 秒，一点没绕开危险窗口。
- 一度把"stopCast"和"unbindService"两条拆会话说成一条。
- **反复出现的模式**：把"没看到日志"当成"没发生"。这次能定案，靠的是把
  `TEARDOWN` 的发送数和应答数分别数出来（4 vs 0），而不是读日志时的印象。

### 5702 的固件事实（本轮新增，CONFIRMED）

```
0x100170bb0  _iap2_wifisharing_RequestAccessoryWiFiConfigurationInformation  (140B, 35 条指令)
  ├─ 0x100170be4  bl _iap2_identification_checkRequiredMsgIDs(session, 0x1001b40c0, 2, &flag)
  ├─ 0x100170be8  cbz w0 → return 0           组不成立就不发
  ├─ 0x100170bf4  mov w1, #0x5702
  ├─ 0x100170c04  bl _iAP2MsgInit
  └─ 0x100170c10  bl _iap2_sessionControl_sendOutgoingMessage   ← 全文唯一一次
0x100170cb8  _iap2_wifisharing__startFeatureFromDevice
  ├─ 0x100170d48  mov w1, #0x16                feature 22
  └─ 0x100170d58  bl 0x100170bb0               ← 全 __TEXT 唯一调用点
```

即 **5702 是 feature 22 的启动动作，一个会话一次，没有循环、没有定时器**。
扫描 `__TEXT` 所有 `BL` 只有 0x100170d58 一处。**20069 的"只发一次"是固件行为，
20068 以前的"每 5 秒重发"是我们自己发明的。**

必填组 `0x1001b40c0` 两项 12 字节：`{0x5702, 1, 1}`、`{0x5703, 0, 1}`。
方向的标定靠邻组 `0x1001b40a8` = `{0x5700,0,1},{0x5701,1,1}`，而
`_iap2_wifisharing_RequestWiFiInformation @0x10017020c` 在 0x10017024c 把入参 ID 与
0x5700 比较 → 5700 是手机收、5701 是手机发 → **1 = 手机发，0 = 车机发**。
第三字段两组四项恒为 1，语义未知，标 OPEN。

顺带交叉验证：这 4.3MB 的 sha256 `2b0a2010…c4fe` 与仓库里已有的
`evidence/iap2-pending-ack-recovery.json` 的 `source_sha256` **完全一致**，
说明拿到的是同一份 accessoryd。

### 20070 改了什么

不是"再改一次 5702"，而是补上一个真漏洞：45 秒退避只在进程内，CarWith 一重启就没了。

- `carRefusedMsAgo()` 从落盘标记算，时效 45s，`attempt()` 里读一次传给
  `CarPlayRunner` → `Bootstrap.negotiate`；
- `Bootstrap` 在 `routes.wifiAnnouncement` 分支**看到标记就直接抛
  `CarHoldsPreviousSessionException(0, withheldMs)`，一个字节都不发**；
- `CarHoldsPreviousSessionException` 加 `withheldMs` 参数，区分"问了没人应"和
  "根本没问"。

### 顺带发现的两个真 bug

1. `markCarBusy()` 的条件是 `stage==DETECT`，但真车失败停在 **AUTH（"车机身份与签名"）**，
   所以这个标记**从来没被写过**。改成按异常类型判定。
2. 如果 withheld 的失败也刷新标记，45 秒窗口会被不断往后推、**永远不过期，车机再也
   等不到下一问**。只有 `withheldMs<0`（真问过被拒）才写。

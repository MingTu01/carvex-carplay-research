# 2026-11-04

## 断开重连不上（第二次必挂）——根因与修复 build 20050

**现象**：CarWith 自带断开按钮，第一次断开重连正常，第二次断开后车机不再回 iAP SYN，只能重启车机。

**根因**：`SessionController.close()` 先 `activeAir=null`，再 `Thread.sleep(8000)` 兜底 forceClose。
服务销毁时 attempt 的 finally 与它同时进行，而 terminator 真正跑起来时读 `activeAir` 已是 null
→ **整会话 TEARDOWN 一次都没发**（车机在 8 秒里一直以为会话还活着）。

**日志量化**（build 20049 单份日志，35 个 session）：
- 走到过 SETUP 的会话 3 个：`e45c8ead`（Wi-Fi 掉线路径，有 TEARDOWN）、`64bb7243`（183 次心跳后消失）、`79055155`（8 次心跳后消失）
- `TEARDOWN begin` 只有 1 次，`session resources released` 0 次
- 即：app 主动断开的路径 100% 漏发 TEARDOWN

**修复**：`attempt()` 加 `ownedAir: AtomicReference<AirSession?>`，cleanup 用它而不是 `activeAir`；
`close()` 去掉 8 秒延迟，立刻在守护线程跑 `forceClose()`。

**为什么这次能让车机松手**：iPhone 断开会发 TEARDOWN，车机当场释放；我们不发，车机把会话留在半开态，
之后 RFCOMM 照连但永不发 SYN（NO_SYN），且能跨链路断开维持 40 分钟以上（用户实测）。

## 20050 实测失败：入口根本不是我们以为的那个（build 20052 修正）

**20050 装车后第二次断开照样挂**，而且日志证明 TEARDOWN 那套修法在这条路上无效：

```
11-04 00:26:11.764  am_kill : [0,389,...,200, stop com.baidu.carlife.xiaomi due to from process:com.miui.carlink]
11-04 00:26:31.672  am_kill : [0,7216,...,200, stop com.baidu.carlife.xiaomi due to from process:com.miui.carlink]
```

`am_kill` 的 reason 是 `stop <pkg> due to from process:<caller>`，对应
`ActivityManagerService.forceStopPackageLocked` —— **CarWith 每次断开都直接
forceStopPackage 我们的包，SIGKILL**。`onDestroy` / `close()` / `cleanup` 一行都不跑，
所以 TEARDOWN 永远发不出去。这条判断我之前下错了，得记住：
**"我们被杀了"和"我们被要求退出"是两件完全不同的事，先看 am_kill 再谈清理逻辑。**

附带：`BridgeStore.log` 是 Channel + 协程异步落盘，进程被 SIGKILL 时最后几行会丢，
所以"日志里没有收尾"不能单独当证据；判定必须靠 logcat（logd 持有，进程死了还在）。
20052 已把 onCreate/onStartCommand/onUnbind/onDestroy/close/teardown 全部打 logcat，
tag = `CarVexLife`。

## 真正的线索：RST 才是让车机重新开口的那一下

同一份日志里两次重连，差别只有一处：

成功那次（becd1bf3）：
```
16:26:18.293 iAP frame RX 40/123/48/1/49 csm=5703   ← 车机在新通道上重传旧会话的包
16:26:18.294 iAP pre-SYN data rejected; sending RST and awaiting peer SYN
16:26:18.294 iAP frame TX 10/0/0/0/0                ← 我们发了 RST
16:26:18.310 iAP frame RX 80/71/0/0/16              ← 16ms 后车机补发 SYN
```
失败那次（c3f137f2）：只发 Detect，车机 7 秒一声不响 → `NO_SYN`。

结论：车机静默不是"它不在了"，而是**它仍认为上一条链路是活的，没有理由再提 SYN**。
20052 改成第一次字节超时后先发 `Frame(0x10,0,0,0)`（RST，seq 归零，和 pre-SYN 那条路径一致）
再发 Detect。健康路径不受影响（车机 100ms 内先开口，走不到这个分支）。
测试 `silentPeerGetsOneRstThenDetectAndThenNoSynFailure` / `assertRstThenDetection` 钉住顺序。

## 20052 实测：RST 有效，墙往前挪了一层（build 20053 继续）

**RST+Detect 确认有效。** 三个连续会话全部拿到车机 SYN，进到 AUTH：

```
16:43:02.623 [fd88db84] iAP first-byte deadline 2000ms; sending RST+Detect
16:43:02.625 [fd88db84] iAP frame TX 10/0/0/0/0
16:43:02.657 [fd88db84] iAP SYN body: ...        ← 车机立刻回 SYN
16:43:03.480 [fd88db84] stage WIFI  → 16:43:04.359 stage PAIR  → 成功跑 24 秒
```
之前同样的位置是 7 秒无声 → NO_SYN。**静默的车机不是死了，是它认为旧链路还活着。**

**新的墙（第二个断开之后）**：iAP 全过（SYN/AUTH/WIFI/Bonjour 都通），卡在车机的 AirPlay 控制口：

```
16:43:34.082 [0231f390] control connect failed source=BOOTSTRAP at 192.168.0.1:7000 ... ECONNREFUSED
16:43:34.092 [0231f390] control connect failed source=BONJOUR  at fe80::cafe:fff:fe29:36de:7000 ... ECONNREFUSED
```
两个候选 10ms 内都被拒 → 车机在释放上一段 AirPlay 会话时把 7000 的监听关了。
下一轮（16:43:37）更进一步：iAP 收到 5702（StartIDPS）之前连 ACK 了 6 帧，到 5702 就装死，
重传 13 秒后放弃。同一个原因，只是位置更靠里。

**20053**：`AirSession.openControlSocket()` 改成候选列表重走 4 轮、每轮间隔 2 秒。
拒绝是瞬时的，等的是那 2 秒；iAP 链路保持不断，不需要整段重连。
（整段重连的代价很大：一次 attempt 一结束，CarWith 20ms 内就 forceStop 我们。）

## 车机死机的直接原因（build 20055）

`ac056f90` 16:50:57 那一轮：车机收下 StartIDPS（0x5702）后**连 ACK 都不回**，我们按 1 秒一次
重传到第 12 次，16:51:12 收到 `Connection reset by peer` —— 车机屏幕当场冻住。
健康车机回 ACK 是 20~50ms，整份日志无例外。所以"车机不回 ACK 超过 3 秒就松手"是对的。

20055 加了 `IapLink.oldestUnackedAgeMs()` + Bootstrap 里 `SILENT_PEER_ABORT_MS=3s`：
不再往已经死掉的 iAP 栈里灌 12 秒重传。

## 被自己数据推翻的推论：静默窗口（已撤销）

我一度以为"重连前必须静默 ≥20 秒"（<4s 全失败、18.8s/26.3s 全成功），
但把整晚按"上一段会话存活时长 × 静默时长"排开就碎了：

```
长会话 154s → 静默 2.3s → 成功      长会话 153s → 静默 3.1s → 失败
长会话  39s → 静默 2.4s → 失败死机   长会话 324s → 静默 2.7s → 成功
静默 26.2s → 成功   静默 18.8s → 成功   静默 52.1s → 仍然 iAP NO_SYN
```

**静默时长不预测结果，车机自己的状态才预测**，而我们读不到那个状态。
所以 20055 把那条 20 秒规则整段删掉了 —— 留着只会让每次重连白等 12 秒。
教训：相关性看起来再干净，也要拿"反例是否同时存在"去检验，否则就是给自己加延迟。

## 20055 之后的新失败点：Wi-Fi 请求阶段（01:03 那一轮）

20055 装上后自动重连连试两次，都死在同一处，而且**死在 iAP 之后**：

```
01:03:30 1dfcc363  iAP 全通（收到 5703）→ stage WIFI → 只打了 Wi-Fi capabilities
          → 之后 12 秒没有任何进展 → 01:03:49 被 CarWith 收走
01:03:49 b96b8bdd  同样卡在 Wi-Fi 请求阶段 → 01:04:10 被收走
01:04:14 7c9c1601  成功（但这次大哥动手了，不算自动恢复）
```

`Bootstrap` 进 WIFI 阶段是先试"复用当前已连的 Wi-Fi"（要求 SSID 相同且本地地址就绪），
不行才用 `WifiNetworkSpecifier` 主动请求车机 AP。两次失败都没走到 `Wi-Fi available; waiting
for link properties`，说明那 12 秒卡在请求/关联那一侧，而 CarWith 大约 20 秒就收走进程。
**下一步若要继续，就在这段加周期诊断（SSID / activeNetwork / 地址是否就绪），别再猜。**

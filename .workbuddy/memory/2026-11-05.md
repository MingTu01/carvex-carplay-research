# 2026-11-05 真车实测（build 20056 → 20058）

## 事件
- 21:42 车机开机；21:42:04 起 CarWith 连续拉起六次，六个不同 PID，全部无 onDestroy。
- 第一次断开 → 自动连上（`79960bfb` 出流 18 秒）；第二次断开 → 卡住 → 车机黑屏 → 自动重启。

## 关键结论
1. **重试不是我们的，是 CarWith 的**：我们失败后 `status.failed` → `stopSelf` → CarWith
   `CMD_DISCONNECT_CAST` → `carlife need reconnect:true, remaining count:4` → 3 秒后重新拉起。
   进程内那个 `while(isActive)` 循环依然从未执行过。
2. **`found=0 seen=0 services=[]`**：车机那两轮真的没广播 `_airplay`，不是被我们的筛选门丢掉。
   第 3 次浏览开始后 1.05 秒就发现 → 车机冷启动广播约需 45 秒。
3. **`failure:` 永远写不进文件**：进程在 onFailure 之后 13 毫秒被 SIGKILL，Channel 异步落盘没刷。
   20058 改为同时写 logcat（tag `CarVexFail`），那里由 logd 持有。
4. **黑屏起点是 CarWith 强杀**，不是我们的重传：21:44:12.369 车机 RTSP 主动 EOF（比黑屏早 16 秒），
   之后那 10 次 5702 重传是对着已死的协议栈在喊。
5. **邀请头没有 features/pk**（只有 host/user-agent/airplay-receiver-device-id）→ "邀请当端点"
   不满足 SecurityRouting 对 DISCOVERY 源的 feature evidence 要求，这条路关闭。

## 改动
- 20057：`ReceiverDiscovery.await(extendOnInvitation)` —— 收到邀请时 15s 后再等 45s，不放 Wi-Fi 租约；
  `endpointWaitMs=75_000` 罩住 15+45。CarPlayRunner 用 AtomicReference 传 publication 给 discover。
- 20058：失败原因 + 终止判定写 logcat（`CarVexFail`）。

## 新问题：车机中途重开 IDPS，我们把它当致命错误（20061 修）

真车 22:29:38（车机刚重启完）：车机发 26 字节控制消息要求重启 iAP 链路 →
我们重同步成功（epoch 1→3）→ 紧接着 `Runtime iAP degraded: IllegalStateException Check failed.`

罪魁是 `RuntimeIap` 轮询循环里**没有消息的裸 check**：
`check(link.generation==authorizedGeneration && link.linkEpoch==authorizedEpoch)`
- `IllegalStateException("Check failed.")` 就是裸 `check()` 的产物，字面上看不出是 epoch 变了。
- `fail()` 把整条 iAP 判死：画音还在，车机发来的 iAP 命令全丢。

**教训**：凡是"授权是否还有效"这类判定，`check` 必须带消息（哪一代、哪个 epoch）。
裸 check 在日志里等于没有信息。

20061 改法：epoch/世代变了就重走一遍识别（最多 4 次，超了带消息放弃）；
`send()` 里同样的裸 check 改成返回 false（丢一条业务提交好过陪葬整条 iAP）；
`negotiate==null` 的直通模式明确不受 epoch 约束。

**待验证**：IDPS 重走是否真能恢复（要等车机再次重开 IDPS）。
大哥反馈按键正常 → 按键不走 iAP，影响面比预估小。

## 量出来的代价：失败一次赔 90 秒

```
22:47:19  车机 7000 → ECONNREFUSED（AirPlay 服务整个不在）
22:47:25  5702 无 ACK（服务回来了但占旧会话）
22:48:23  5702 才 ACK（旧会话释放）
```
机制：我们失败 → 放开 WifiNetworkSpecifier → CarWith 判定投屏结束 → releaseCastCore →
车机拆接收端 → 无线 CarPlay 子系统重启 60~90 秒。**循环有一半是我们自己踩出来的。**

划掉的路：`DISCONNECT_CAST_ACTION` 广播到 forceStop 只有 **1 毫秒**，抢不到 TEARDOWN。

## 20061 / 20062

- 20061：`RuntimeIap` 裸 `check(linkEpoch==authorizedEpoch)` 是 `Check failed.` 的来源 ——
  车机重开 IDPS 时 epoch 1→3，断言必炸 → fail() 判死整条 iAP。改成 epoch 变了重走识别（≤4 次）。
  **尚未被真车触发。** 大哥反馈按键正常 → 按键不走 iAP。
- 20062：`CarNetworkLease` 把 Wi-Fi 租约抬到会话级，跨尝试存活，失败不再放网络。
  `Bootstrap.network` 加 `lease` / `reuse` 两个可选入口；`attempt()` 的租约参数可空，无租约时行为不变。

**教训**：凡是 Android 里"撤掉某个请求"的动作，都要先问一句：**撤掉这件事本身，对端会怎么解读？**
`WifiNetworkSpecifier` 的撤掉在 CarWith 眼里不是"这一轮失败"，而是"投屏结束了"。

### 20063（静默不退场 + 5702 退避重发）—— 未被验证
手机侧断 wifi 压出来的不是 5702 静默，是 **`ENETUNREACH`**：车机热点整个消失，链路先被打断，
静默护栏根本没有机会参与。**只要断的是网络，这条分支就永远压不出来。**

### 20064（CastRetention）—— 部分生效，但没解决问题
改法：`VendorCastHost.close()` 里的 `stopCast()` 交给 `CastRetention` 推迟到会话真正结束再补发。

结果：
- **有效**：`launcher receiver stopCast` 这一行确实没再出现（上一版每次都出现）。
- **无效**：CarWith 照样拆投屏、照样 forceStop。真正的触发点是我们的 **`unbindService`**：
  ```
  23:37:33.737  ConnectivityService: [615 WIFI] CONNECTED -> DISCONNECTED
  23:37:33.882  ActivityManager: unbindService [...CarlifeConnService] from PID:10107  ← 我们解绑
  23:37:33.887  CastController: enter releaseVirtualDisplay
  23:37:33.956  CarlifeConnService: onDestroy
  23:37:33.958  forceStopApp:com.baidu.carlife.xiaomi
  ```
  只按住 stopCast 不够，绑定关系一断，CarlifeConnService 就没有客户了，服务自己 onDestroy。

### 真正的大头：车机自己要 40~47 秒
两次手机侧断连，从链路丢失到车机肯接受 iAP：

| 轮次 | 掉线 | 第一次探测 | 最后一次失败探测 | 成功 | 掉线→成功 |
|---|---|---|---|---|---|
| 23:23 | 10.7 | 24.3 | 30.3 | 50.3 | **39.6 s** |
| 23:37 | 33.7 | 44.4 | 58.2 | 20.5(+1min) | **46.8 s** |

两种模型都能解释这两组数：
- **A：车机需要"安静 20 秒"**（每次探测重置计时）→ 那么少探测就能提前成功；
- **B：车机固定要 40~47 秒**（我们的探测无关）→ 那只能等。

**没有第三组数据无法区分**，需要一次"持续每 5 秒探测"的对照。

### 顺带发现的真 bug（车机重启时暴露）
```
failure: IllegalStateException iAP link changed during bootstrap
  at Bootstrap.negotiateSession$checkGeneration(Bootstrap.kt:381)
```
车机在 `Bootstrap` 引导中途重开 IDPS 时，`checkGeneration()` 抛的 `IllegalStateException`
落在 `SessionController` 的终止性异常集合里 → 直接放弃整条会话（stage FAILED，不再重试）。
20061 只在 `RuntimeIap` 外层修了这件事，`Bootstrap` 内部这道硬检查还在。**待修。**

### 教训
- 只改"我们主动发的某条命令"往往不够，要看**整条绑定/服务生命周期**：stopCast 挡得住，
  unbindService 挡不住。
- CarWith 的节奏（杀进程 → 隔 10~22 秒再拉起）会主导重连总时长，我们自己的重试循环根本没在跑，
  因为进程在第一次失败后就被 SIGKILL 了。

**20067** `ab88ee5`：安静期标记根本没落盘。`markCarBusy()` 写在 `onFailure` 里，
而 `onFailure` 在 `cleanup.close()` 之后才跑，此时 unbind 早已发出；而且用的是 `apply()` 异步写。
实测 `failure` 到 SIGKILL 只隔 **1 毫秒**。

### 新发现：`onFailure` 会被整段跳过
那一刻的失败是 `CancellationException`，`ensureActive()` 直接把 launch 结束掉，
`onFailure` 一句都不执行——logcat 里连 `CarVexFail` 都没有。
20067 在 catch 里补了一行同步 logcat（`attempt cancelled: <类型> jobActive=<bool>`），
以后能区分"本地超时"和"被外部取消"。

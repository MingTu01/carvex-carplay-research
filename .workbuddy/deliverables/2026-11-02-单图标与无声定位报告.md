## 0. 一句话

**画面和声音是两个互不相干的问题，都不是"连不上"。**

- **画面**：视频流在交付 23 帧之后彻底停摆 20～58 秒，车机只是把最后一帧冻在屏幕上。
- **声音**：协议层全部通过、包一直在发（46.5 包/秒，连续 42 秒），但车机一声没出。
- 另外发现一个**必现的会话自杀点**：车机发 `changeModes`，我们回了个畸形应答，车机 422，我们主动把整条会话拆了。

## 2. 画面：23 帧之后一个字都不发了

### 2.1 事实

```
10:56:11.480  AVC selected name=c2.qti.avc.encoder hardware=true size=1024x600 fps=30 bitrate=2396160
10:56:11.532  Splash page shown for 6000ms
10:56:12.384  hb video=11/275ms        ← 启动页画了 11 帧
10:56:17.389  hb video=11/5281ms       ← 5 秒没有新帧
10:56:17.534  CarWith host owns the frame source; front surface disabled, so no P frames while still (latency first)
10:56:17.676  Host prepared a cast display; the app-owned page is released
10:56:18.390  hb video=23/320ms        ← 交接瞬间补了 12 帧
10:56:37.420  hb video=23/19348ms      ← 之后 20 秒，一帧没涨
```

`6fd29fd2` 里更夸张：`10:57:04 video=23/6420ms` → `10:57:46 video=23/42478ms`，
**42 秒里编码器输出为 0**。心跳里的第二个数字就是"最后一帧有多旧"。

### 2.2 机制（这是设计取舍，不是崩溃）

`SessionController.kt:798`：

```kotlin
// Opt-in latency trade: the front surface is the only way a still CarWith picture
// gets a P frame, and it costs a blit per frame plus a few frames of latency.
frontSurface = o.frontSurface && hostOwnsDisplay
```

`SessionController.kt:822-826` 的注释说得更直白：CarWith 拿到编码器的 surface 之后
**不会自己重绘**，所以"静止画面"在 MediaCodec 那边就等于"没有输入"，编码器也就没有输出。
走 `frontSurface` 才有 `EncoderFrontSurface.repeat()` 把手里那一帧再 blit 一次，
换出一个小 P 帧，让媒体流不至于断气。

**而 `frontSurface` 默认是 `false`，并且整个 `app/` 模块里没有任何 UI 入口**
（`grep -rn frontSurface android/app/` → 空）。也就是说：现在这个开关用户根本打不开，
只要 CarWith 接管帧源，静止画面必然把流冻死。这和日志完全吻合。

### 2.3 "一个图标"是什么

车机 H.264 解码器手里最后一帧就是 23 帧里的某一张，之后没数据，它就永远停在那儿。
启动页是渐变底 + 标题 + 收款码（`LocalVideoDisplay.kt:184` `BrandPage`），不是图标，
所以那个"图标"更可能是 CarWith 接管后自己画出来的第一屏——但**它到底是什么，只有让流重新动起来才能确认**。
换句话说：先解决"流不动"，再判断"画的是什么"。

### 2.4 顺带发现的不一致（待验证，不是结论）

帧记录头在两条加密分支里的构造不一样：

- HomeKit 分支 `Wire.kt:156 VideoWire.frame()`：写 `0x05`（关键帧）、`0x08`、`0x10`、`0x20`、`0x58`
- SAP 分支 `AirSession.kt:1324-1328`：**只写** `0x00`、`0x08`、`0x10`

```
ByteArray(128).also{ ByteBuffer...
    .putInt(0, encrypted.size).putLong(8, ntp).putLong(16, timestamp)
} + encrypted
```

同一套头语义不应该因为换了个加密算法就退化。这条**该修**。

但要注意证据边界：`research/protocol/airplay_video_channel/analysis/02-screen-record-format.md:24`
明确写着 `+0x05` 的 bit4 来自 NotSync 输出、`bit7` 来自 APInterestingFrame，
"附件派生不是 NAL IDR 证明；forceKeyFrame 因果链仍 `OPEN-VID-7`"。
所以**不能**说"因为缺 0x10 标志位所以花屏"——只能说两条分支不一致，修一致性，不冒充协议结论。

## 3. 声音：协议全通，包在发，车机不理

### 3.1 事实（`6fd29fd2`，最干净的那次）

```
10:56:56.799  MFi/SAP material ready; SETUP will carry et=16 with ekey/eiv
10:56:56.887  SETUP  cseq=2  bodyBytes=564  → 200 (84ms)
10:57:03.473  Audio SETUP fields category=3 spf=480 controlPort=44970 input=absent dataPort=none
10:57:03.607  SETUP  cseq=36 bodyBytes=346  → 200 (132ms)
10:57:03.608  Audio SETUP accepted category=3 type=100 dataPort=48773 controlPort=null
10:57:03.899  Audio SETUP accepted category=1 type=102 dataPort=53536 controlPort=34315
10:57:03.899  Audio crypto category=1 mode=AES-CTR(MFi/SAP) redEnabled=false payloadOnly=true tagBytes=0 nonceTail=0
10:57:04.600  Compressed RTP category=1 type=102 codec=AAC_LC packets=1
...
10:57:46.2    audio[c1=1953/8ms]
```

- `/auth-setup` → 200，MFi/SAP 签名验过，`et=16 + ekey/eiv` 被接受
- **三个音频类别的 SETUP 全部 200**，车机都分配了 dataPort
- AES-CTR 分支确实生效了（新代码在工作）
- 1953 包 / 42 秒 = **46.5 包/秒**，和 AAC-LC 1024 帧 @48 kHz 的 46.875 完全对得上

**发送节奏、端口、流注册、加密开关，全对。就是没声。**

### 3.2 这说明什么

"SETUP 200" 只证明车机**接受注册**，不证明它能**解开**我们的包。
AAC 解不开时绝大多数解码器是静默丢帧，不会回任何错误——所以日志永远干净。

代码自己在日志里就承认了这一点：

> `MFi audio wire profile has no packet-capture evidence`

这条 MFi 音频线上格式，是照 `06-frame-crypto-aes.md` R-6.1（AES-CTR 同长、无 tag、无 padding、
计数器跨包连续不能每包重建）+ RTF 消息布局推出来的，**从来没被任何一份真实抓包核过**。

### 3.3 已经排除掉的

- ❌ 不是编码器没起来：`Compressed encoder ready name=c2.android.aac.encoder category=1`
- ❌ 不是没发出去：`packets=N` 一直在涨，`audio[c1=N]` 也一直在涨
- ❌ 不是端口错了：`dataPort=53536` 是车机自己给的，我们往那儿发
- ❌ 不是 RED 拖累：`RED offered=false response=null sendRED=false`，纯主块
- ❌ 不是类别 2/3 的编码器配置问题连累媒体流：那两条是 `IllegalArgumentException`（ELD resilience / 配置不匹配），
  独立失败，`other streams retained`

### 3.4 还剩下的可疑点（按怀疑度）

1. **流密钥索引对不上**。音频用 `Crypto.random.nextLong()` 生成 id（`AirSession.kt:1045`），
   再拿它做 `SHA512("AirPlayStreamKey"‖dec(id)‖K)[0:16]`，同时把这个 id 当 `streamConnectionID`
   写进 SETUP（`AudioSetupDescription.playback(...)`）。视频是同一套路且**视频能出画面**，
   所以这条路本身是对的——但如果车机对音频流取的"字典整数"不是 `streamConnectionID` 而是别的字段，
   两边密钥就错开了。`04-kdf-sha512.md` 里 A-46 原文就写着"Receiver 先取字典整数再传给 ForScreen"，
   **具体取哪个字典没闭合**。
2. **RTP payload type 用的是 102 本身**（`MediaAudioPackets.kt:19 wireType(type)=type`）。
   固件 `03-payload-types.md` A03.1 的四字符码→PT 表只有 8 条：`main→0x64`、`alt →0x65`、
   `ared→0x69`、`mred→0x68`、`auxo→0x6a`、`oovc→0x6b`、`axrd→0x6c`、`ovrd→0x6d`，
   **没有 0x66（102）这一条**。128 字节头属于自己编的字段，不算数。
3. **加密到底该不该开**。SETUP 里带 `et=16 + ekey/eiv` 是给屏幕流的；音频这条要不要也加密，
   文档里没有正面结论。AirPlay 1 的音频默认是可以不加密的。
4. **车机是不是根本没在听这条流**。CarWith 自己可能也有一条音频通道（BT A2DP 或它自己的 CarLife 通道），
   两路抢，车机选了另一路。

### 3.5 一个能一刀切开的实验

把音频 payload 改成**明文直发**（不套 CTR），其余不动，跑一次：

- 如果**有声音/有噪音** → 密钥或 CTR 那条路错了，问题在密码层，明文都能通说明路由和 PT 都是对的。
- 如果**还是没声** → 车机根本没在看我们这条流（PT 或路由问题），先别折腾密钥。

改动只有 `CarPlayCompressedAudio` 里一行：`sapCipher=null` 时走原样发送。
这个实验只需要跑一次，就能把上面 4 个可疑点砍掉一半。

## 4. 新发现：一个必现的会话自杀点

### 4.1 现场

```
10:56:38.121  OBSERVE rtsp command type=changeModes payload={params={resources=list[1]},type=changeModes}
10:56:38.124  SEND POST /command cseq=53 bodyBytes=91 command=modesChanged
10:56:38.130  RESPONSE ... status=422          ← 车机拒绝
10:56:38.130  channel source=modes-writer StatusException RTSP POST /command status 422
10:56:38.131  channel failure StatusException
   → 整条会话开始拆：VideoEncoder / CarPlayCompressedAudio / 所有 Socket 全关
10:56:38.390  screen TEARDOWN accepted
```

20 秒前还活得好好的会话，因为一个模式通知被拒，被自己拆了。

### 4.2 根因（两处，都可证）

**第一处：把畸形通知发给车机。**
`AirSession.kt:842-848`：

```kotlin
private fun eventReplied(request:RtspMessage,status:Int,body:ByteArray){
    if(status!=200||body.isEmpty())return
    val command=Plist.dictionary(request.body)
    if(command["type"]!="changeModes")return
    val reply=Plist.dictionary(body)
    val notification=mapOf("type" to "modesChanged","params" to reply["params"])   // ← params 可能是 null
    if(modeOutput.trySend(notification).isFailure)throw IOException(...)
}
```

而 `command()` 里 `changeModes` 有两条"拒绝"出口，回的都是**不含 params** 的：

```kotlin
val proposed=screenModes.propose(params)?:return 200 to Plist.encode(mapOf("status" to 1))
...
if(resource==1&&screenOwnership?.invoke(proposed.owner==1)!=true)
    return 200 to Plist.encode(mapOf("status" to 1))
```

拒绝 → 回 `{status:1}` → `reply["params"]` 是 null → 转发出去一个 `params=null` 的 `modesChanged`。

算术上可以钉死：整晚所有被车机**接受**的 `modesChanged` 都是 **553 字节**
（cseq=4/35/37/40/41，全部 200），唯独这一次是 **91 字节**，全部被拒。
553 正好等于 `modes()`（`{type, params: screenModes.params()}` 完整两资源 + 三 appState）的长度。

**第二处：一有非 2xx 就拆会话。**
`AirSession.kt:185-189`：

```kotlin
scope.launch{
    try{for(notification in modeOutput){
        val control=client?:error("Modes before control session")
        control.plist("POST","/command",notification)
    }}catch(t:Exception){if(isActive)channelFailure("modes-writer",t)}
}
```

`control.plist` 拿到 422 会抛 `StatusException`，然后 `channelFailure` 把**整条**会话判死。
一个"模式通知被拒"和"传输断了"是两件事，不该同等对待。

### 4.3 修法

1. `eventReplied`：`reply["params"]` 为 null 时**不要转发**（拒绝已经通过事件的 200 + status 表达了）。
2. `modes-writer`：区分"传输异常"和"业务被拒"。非 2xx 只记一行日志，
   不 `channelFailure`；只有 `IOException` 才走拆会话。
3. （可选，需证据）`screenOwnership` 拒绝车机拿走屏幕是否合理——
   拒绝屏幕归属本身可能是对的，但要用日志把"为什么拒"写清楚。

## 5. 关于"反编译 CarPlay 组件、在 Java 里复刻"这个方法

### 5.1 他说的是什么

原话拆开：

- **"他提供 carplay 的组件"** —— 上游手里那个**能真跑通**的 CarPlay 实现（这里是明途车机固件里的
  AirPlay 接收端，`AirPlaySender` / `AirPlayReceiver` / `AirPlaySupport` / `APTransport` / `CoreUtils` 那五个镜像）。
- **"通过日志或者抓包来反编译"** —— 遇到不一致，不要去翻苹果的公开 AirPlay 文档猜，
  而是去看那个**已经跑通的组件实际怎么做**：打日志、抓线上字节、用 IDA/Ghidra 读它的机器码。
- **"然后再 java 中复刻出来"** —— 把它真实的行为一比一抄进我们的 Kotlin/Java，
  包括字符串常量、KDF 公式、字段偏移、位含义。
- **"这样就可以通用了"** —— 因为抄的是"真实存在且能工作的行为"，
  而不是"文档上应该是这样"，所以不用给每个车型写一条分支。

一句话：**以能跑的那个二进制为唯一真相，而不是以文档为真相。**

### 5.2 这套方法这个仓库已经在用了

`research/` 下那些 `analysis/*.md` 全是这个路子，而且做到指令地址级别：

```
0x2519c0d84: mov  w11, #0x3302       ; 允许集合的位图
0x2519c0d94: add  x8, x8, #0xc        ; 元素区起点 = 包基址 + 12
```

连 `SHA512("AirPlayStreamKey"‖dec(i)‖K)[0:16]` 这种公式，都是从
`0x251aa97d4 x8 = "AirPlayStreamKey"` / `ASPrintF(&name1,"%s%llu",...)` 反推出来的。
**方案不用换，本来就是这套。**

### 5.3 但有三条纪律，不守就会翻车（`AGENT.md` 已经写了）

1. **唯一权威是"对端真正在跑的那个二进制"**。Android 代码、第三方开源实现只能当索引，不能当证据。
   本轮就踩了一次：我一度想说"帧头缺关键帧位就是花屏根因"，
   去查 `02-screen-record-format.md:24` 发现那个位的来源是 NotSync 输出，
   文档自己标着 `OPEN-VID-7`——于是只能降级成"两分支不一致，修一致性"。
2. **每条结论标 `CONFIRMED` / `INFERRED` / `OPEN`**，不许把"读代码猜的"写成"已确认"。
3. **`OPEN` 项不能靠"试出来了"就关掉**——要把试出来的现象反推回固件里找到对应指令，才算闭合。
   否则下一个车型上会原样复发。

### 5.4 但这一轮，反编译不是瓶颈

本轮两个问题（没画面 / 没声音）卡的地方是**"车机到底收到了什么、怎么处理的"**，
这个反编译给不了答案——我们缺的是**线上字节**。所以这轮该做的是抓包，不是继续读机器码：

**抓包（不用 root）**
1. 手机装 PCAPdroid，选"抓本机流量"，目标 IP 填 `192.168.0.1`。
2. 跑一次**能出声的参照**（车机自带 CarWith 正常连接），再跑一次我们的。
3. 只看几个字段：音频 RTP 的 `len / pt / seq / ts / ssrc`、包间隔、总长 vs AAC 帧长
   （判断有没有 tag/tail）、以及车机有没有往 `controlPort` 回包。

一份这样的抓包能同时关掉：
- `U-2`（SAP 音频线上格式）
- `OPEN-RTP-2`（`pkt+8..11` 到底是不是 SSRC、随不随流变）
- `OPEN-VID-7`（`+0x05` 那两位到底谁在写）
- `OPEN-PORT-1`（controlPort/dataPort 的真实取值与方向）

**比抓包更省事的备选**：直接对车载端的 `AirPlaySender` 继续做静态分析，
用 `grep -a` 已经能捞到关键字符串（这轮就捞到了
`coreUtilsKeyHolder_CreateDerivedKey` / `legacyKeyHolder_CreateDerivedAESKeyAndIVForLegacyStream`
两条并存的 KDF 路径，以及 `AirPlayReceiver` 里 `_GetDataStreamSecurityKeys` 用的是
`DataStream-Salt`）。要把它们各自对应到哪条会话路线，得下钻到调用点。

## 6. 建议的下一步（按性价比排）

| # | 动作 | 成本 | 能关掉什么 |
|---|---|---|---|
| 1 | 修 `changeModes` 422 自杀链（4.3 三处） | 小 | 会话能活过 20 秒，否则后面全是白测 |
| 2 | 音频改成明文直发跑一次 | 极小 | 一刀切开"密码层错"vs"车机没在听" |
| 3 | `frontSurface` 打开（顺带给它个 UI 开关） | 小 | 画面能不能动起来 |
| 4 | 视频帧头两分支统一（补 0x05/0x20/0x58） | 小 | 排除头部不一致 |
| 5 | PCAPdroid 抓一份参照包 | 中（要装东西） | `U-2`/`OPEN-RTP-2`/`OPEN-VID-7`/`OPEN-PORT-1` 一批 OPEN 项 |

**必须先做 1**，否则每次会话最多 20 秒就自己死，2～4 测不出东西。
**2 和 3 可以一次出包一起测**：一个看画面动没动，一个看有没有声。

## 7. 需要你回答的一个问题

**用车机自带的 CarWith 正常连接（不走我们这套）时，车机喇叭有声音吗？**

- 有 → 说明车机确实有一条能出声的路，我们要么复刻它，要么干脆别自己发音频、让 CarWith 去发。
- 没有 → 说明这台车机的音频本来就不走这条路（可能是 BT A2DP），那"我们发的 AirPlay 音频没声"就不是 bug，
  问题变成"我们抢了 CarWith 的主音频归属，反而把出声的那条路堵了"。

这一条决定第 2 步之后往哪走，比再读一天机器码有用。

# 导航中触屏失效：根因与结论（2026-11-03）

## 一句话结论

**CarWith 的导航语音（CarPlay audio category 2）在会话中途做的那次 SETUP，会让车机交出输入焦点且永不归还 —— 这就是"一开导航触屏就死"的全部原因。**

已修复并真车验证（build 20045，提交 `34f5f18`）。代价是导航播报仍然静音（它本来从未响过），媒体音频与触屏均正常。

---

## 一、验证方式（这是唯一一次基线经核实的对照实验）

同一次装包、同一台车、同一会话内，只改一个变量：

| 条件 | 导航开始后的触摸 | 证据 |
|---|---|---|
| 拦掉 cat2 的 SETUP | **全程正常** | 会话 `2f8114ca`：97 条报告，跨度 `15:15:31 → 15:17:12`，导航开始于 `15:16:10` |
| 不拦（之前五次） | 立刻归零，退出导航也不恢复 | `8669f557` `7dbf1b68` `4df209d1` `e0fabeae` `d301db4c` |

开关生效的直接日志证据：

```
15:16:10.037  Audio category=2 dropped by navAudio=false; no SETUP attempted
15:16:10.293  mix_notify_start_navi
15:17:12      仍有触摸报告
```

## 二、精确时序（每个会话都一致，音频永远早于导航动作）

```
T+0.0s  最后一条触摸（就是点"开始导航"那一下）
T+0.1s  cat2 要流 → 100/alert 400 → 回退 101/default → 激活失败
T+0.2s  mix_notify_start_navi
之后     0 条触摸
```

关键事实：**触摸消失发生在我们做任何动作之前，且车机全程没有发任何命令解释这件事。**

## 三、机制

车机为语音流让出输入焦点后**永不归还**。这与历史上小爱（cat3）的坑是同一个机制 ——
`AudioDebugConfig.speechAltPcm` 的注释里就写着"用完小爱之后触屏失效，只有重启车机能恢复"。
当初的修法是让 cat3 别去抢 `type 100`；而 cat2 一直在会话中途做同一件事，所以每开导航必死。

**因此先前所有"重新武装输入"的尝试都打在空处**：不是车机不认，是我们自己把焦点送出去了。

## 五、会话三态模型

| 状态 | 触摸 | 画面 | 解除方式 |
|---|---|---|---|
| 正常会话 | 有 | 有 | — |
| 导航中（未修复版本） | 无 | 有 | 退出导航**不行**；导航仍在时重连也**不行** |
| 导航结束 + 重连 | 有 | 有 | 重连即可（22:10、22:16 两次实测） |

注：早期"只有重启车机能清"的说法不准确 —— 真实条件是**导航还在跑**。导航一结束，重连一次就恢复。

## 六、屏幕流不能在会话中途重建（另一条独立结论）

对照组（非导航态、画面和触摸都正常时）触发 `restartScreen`：

| 实验 | SETUP/RECORD | 新端口 | 帧 | 触摸 | 画面 |
|---|---|---|---|---|---|
| 同 `streamConnectionID` | 全 200 | ESTABLISHED 且在收 | 继续涨 | 4→68 | **永久黑** |
| 新 `streamConnectionID` | 全 200 | ESTABLISHED 且在收 | 1806 在涨 | 68 | **永久黑** |

⇒ **屏幕流一旦被 TEARDOWN，这条会话内车机再也不会把显示绑回来。** 只能重连恢复。
`restartScreen` 入口仅保留给 ADB 调试，主路径不再自动触发。

## 七、导航语音为什么没声音（待修）

cat2 的源是 **16000 Hz 单声道**，我们按 **AAC_ELD 48000/2** 建流：

```
Audio category=2 PCM 16000 Hz channels=1
Audio category=2 local AAC_ELD/48000/2
Compressed audio category=2 failed: IllegalArgumentException
    ELD resilience/SBR configuration unsupported      ← AacConfiguration.kt:24
```

Android 的 AAC-ELD 编码器回写的 csd 里带了 SBR/resilience 位，被我们的解析器拒绝。

### 修法（两条必须同时满足，缺一不可）

1. **复用会话建立时那条预热流，绝不在中途 SETUP。**
   预热是安全的：`15:15:23` 那次 cat2 SETUP 被接受（dataPort 54943）之后触摸照常。
2. **让那条预热流真正能编码。**
   `Pcm16Converter` 已支持单声道→双声道上混，链路上不缺能力；
   待定的是 ELD 配置：要么调整 MediaCodec 的 ELD 参数避免 SBR，
   要么让 `AacConfiguration` 容忍 SBR 位并取其核心速率。两者都要真车验证。

# 十、续篇：导航音频与重连不上（build 20047）

## 10.1 导航没声音：不是车机拒绝，是我们自己把流弄死了

同两份日志里两行并排，结论没有余地：

```
12:17:03.921  Audio SETUP accepted category=2 type=100 dataPort=50122
12:17:03.973  Compressed audio category=2 failed: IllegalArgumentException
              ELD resilience/SBR configuration unsupported
```

`100/alert` 车机是**接受**的（dataPort 都给了），9 毫秒后我们自己抛异常把流关了。
根因是源为 **16000 Hz 单声道**，而车机在 `100/alert` 与 `101/default` 上只广告
`outputMask=2008000`（lpcm 48000/2 | ELD 48000/2）—— 我们只能选 AAC-ELD 48k/2，
而 Android 的 AAC-ELD 编码器回写的 csd 带 SBR/resilience 位，`AacConfiguration.kt:24` 直接拒绝。

导航真正开始时还有第二层：

```
12:19:38.335  Audio route refused category=2 type=100/alert status=400
12:19:38.339  category=2 unavailable: Audio stream type=101/default already has a session
```

`type 100` 已被主音频占住 → 400；兜底的 `101/default` 被 **category 3 的预热流**占着，
而那条流整场 **发 0 个包**（心跳恒为 `c3=0/-`，`Audio host callback category=3` 一次都没有；
小爱的声音实际走的是 category 1 的媒体流）。

## 10.2 修法：给它一条自己的、会话建立阶段就建好的 PCM 通道

| 改动 | 位置 |
| --- | --- |
| `pcmAlert` 默认 **true** → cat2 走 `101/default` 裸 PCM 48k/2，不碰编码器 | `AudioDebugConfig.kt` |
| 预热顺序 `3,2,1` → **`2,1`**，category 3 不再占 `101/default` | `CarPlayAudioPlan.bootstrapPlayback` |
| 中途 cat2 PCM 不再被吞：有活着的预热流时 `return false`，落到 `audio.receive(...)` | `SessionController.requestAudio` |

第三条是关键：`HostAudioBridge` 的 `Pcm16Converter` 本来就支持单声道→双声道上混和
16k→48k 线性插值重采样，所以导航 PCM 直接被灌进那条已经存在的流。
**整条链路一条新流都不建**，车机的输入焦点不会被拿走 —— 第五节那个触屏修复不会回退。

## 10.3 重连不上：抓到了现场

重装 APK 打断活会话，正好复现。每一次尝试都是同一个形状：

```
RFCOMM selected initiator=phone; peer matched        ← 蓝牙通
stage DETECT
iAP NO_SYN: no peer SYN within 7000ms                ← 车机不肯开新的 iAP 会话
```

也就是**车机仍然占着上一个 AirPlay 会话**。两条新事实：

1. **它会自己释放，约 2.5 分钟。** 15:25:39 起连挂 5 次，15:28:05 自己连上了。
   「必须重启车机」多半是没等够 —— 现在重试状态会直接写「车机仍在释放上一个会话（通常 3 分钟内自动恢复）」。
2. **原有的 `refreshSdpAfterNoSyn` 从来没生效过。** `startSession` 的失败收集器会 `stopSelf()`，
   CarWith 立刻把服务拉起来 → 新的 `SessionController` → 实例字段的标记丢失。
   日志证据：`NO_SYN`（15:47:21.527）之后 350 ms 就是 `freshness=unverified`。
   已改为落盘（10 分钟时效），跨服务实例有效。

## 10.4 新增：控制面存活看门狗

`/feedback` 每 ~2 秒一次，车机每次回 200。所以「20 秒内一条控制面消息都没有」只可能是对端不在了。
以前 `ctrlRxAge` 只打日志、没有任何人消费它：走远之后阻塞式 `read()` 不会报错，
会话永远停在 STREAMING（界面显示已连接、实际一条命令都发不出去）。
现在判定为普通 IO 失败交给重试循环，重试会重新走蓝牙 + Wi-Fi + iAP 握手。

## 10.5 待验证

- `101/default` 的 PCM 是否真的出声。它在真车上被 SETUP 接受过、也广告了
  `audioLatency outputLatencyMicros=33700`，但从来没承载过实际 PCM（c3 恒 0 包）。
  判据在日志：`Audio category=2 PCM source=16000/1 target=48000/2`、
  心跳 `c2=<packets>/<age>` 持续上涨、`Audio host category=2 blocks=...` 每 5 秒一行。
- 若 `101/default` 被证实无声，退路是把 cat2 的 PCM 直接混进 category 1 的媒体流（媒体那条是实证出声的）。

# 十一、续篇 2026-11-07：规则是"不许请求"，不是"不许用某条路由"

## 11.1 又栽了一次

1.0.83 让语音走 `100/speechRecognition`，1.0.85 改走 `101/compatibility` —— **两版都复现了触屏失效**。
第二次尤其说明问题：`101/compatibility` 在 `/info` 里明明广告了 `可收[PCM16/48000/2]`，
SETUP 也照样回 **400**。既然两次的目标路由完全不同、结果一样，那变量就不是路由。

第五节那句结论要按字面读：**拿走输入焦点的是"发起 SETUP"这个动作本身**，
车机回 200 还是 400 都无所谓，请求已经发出去了。

## 11.2 两处漏网的中途 SETUP（都在 category 3）

| 位置 | 触发时机 | 后果 |
|---|---|---|
| `startAudio` → `requestAudio(3, prime=false)` | 小爱一出声 | 要 `101/compatibility` → 400 + 触屏没了 |
| `startSpeech` → `requestAudio(3, prime=true)` | 车机发 Siri/语音动作（`directVoiceAction`，`raw==2`） | 同上 |

注意第二个虽然叫 `prime`，但它发生在**会话中途**，`prime` 只是让它绕过了当时那条只针对
category 2 的门禁——预热的"安全"仅指**会话建立阶段**，不是这个布尔值。

## 11.3 现在的约束（1.0.86）

`SessionController.requestAudio` 里：

```kotlin
if(!prime){                                   // prime 只有会话建立阶段会传
    if(audio.laneAssignment()[category]!=null)return false   // 灌进活着的通道
    /* 没有活通道就丢弃，并限流写一行日志 */
    return true
}
```

- 不分类别、不看路由、不关心车机回什么。中途一律不建流。
- 小爱的声音并进活着的通道（`HostAudioBridge.routeFor`：3 → 2 → 1），
  16k/1→48k/2 转换和 3>2>1 让路仲裁都在那里。
- `startSpeech` 置空：语音预热只可能换来 400，没有任何收益。
- 手动「CarPlay 测试音」也不再自建媒体流，没有活通道就取消。

## 11.4 三路分离正式关闭

这个接收端能发 PCM 的只有两条：`100/media`、`101/default`。
`101/compatibility` 实测 400，`102/media` 只收 AAC_LC 而 CarWith 只采 PCM（SETUP 200、整场 0 包）。
**物理上只有两个位置**，所以三路音量不可能同时分开。

设置页的「三路音频分离」开关、顶部「会话诊断」面板、设备详情页的诊断面板、
「通知使用权」入口，全部移除（1.0.86）。协议层的 `separateLanes` 参数保留，
留给真的广告了第三个 purpose 的接收端。

诊断数据仍然在 logcat 里：`adb logcat -s CarVexDiag:I`，5 秒一条（video / lane / route）。

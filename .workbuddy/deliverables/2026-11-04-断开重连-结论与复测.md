# 断开重连：今晚的结论与明天的复测步骤

日期：2026-11-04 凌晨（build 20047 → 20055）
状态：**可用但未验收**。手动重连后画面/触摸/音频正常；**自动重连 0 次成功**。

---

## 一、一句话结论

蓝牙那层的墙已经拆掉了（iAP 能在被打断后重新开口），现在卡在**手机加入车机 Wi-Fi** 这一步；
而车机被反复打断后会进入"仍认为旧会话活着"的状态，表现位置随恢复程度逐层往里挪。

---

## 二、今晚确认的事实（都有日志证据）

### 1. CarWith 断开我们，是 forceStopPackage（SIGKILL）

```
01:03:49.246  am_kill : [0,10532,com.baidu.carlife.xiaomi,200,
              stop com.baidu.carlife.xiaomi due to from process:com.miui.carlink]
```

每一次会话结束都是这样，无一例外。含义：
- `onDestroy` / `close()` / `cleanup` **没有机会执行**，我们发不出任何收尾报文；
- 所以"让进程在退出时发 TEARDOWN"这条路**永远行不通**——20050 就是栽在这里。

### 2. 车机静默 ≠ 它不在了；RST 能让它重新开口

同一份日志里，重连成功的那次与失败那次只差一条 RST：

```
16:26:18.293  iAP frame RX 40/123/48/1/49 csm=5703   ← 车机在新通道上重传旧会话的包
16:26:18.294  iAP pre-SYN data rejected; sending RST
16:26:18.294  iAP frame TX 10/0/0/0/0                ← 我们回一条 RST
16:26:18.310  iAP frame RX 80/71/0/0/16              ← 16ms 后车机补发 SYN
```

失败那次只发 Detect，7 秒一声不响 → `NO_SYN`。
**20052 之后**：首字节超时改为先 RST 再 Detect，接着三个连续会话全部拿到 SYN。
→ 这一层修好了。

### 3. 车机"没恢复好"会在不同层现形（同一根因）

| 静默/打断后到达的深度 | 现象 |
|---|---|
| 最浅 | RFCOMM 通，但车机不发 SYN → `iAP NO_SYN` |
| 中 | iAP 全通，但车机 AirPlay 控制口 `192.168.0.1:7000` → `ECONNREFUSED` |
| 更深 | 收到 StartIDPS(5702) 后不再 ACK → 12 秒后 `Connection reset by peer`，**车机屏幕冻住** |

所以"卡点变了"不等于"修坏了"，多数是同一件事往里面挪了一层。

### 4. 车机死机的直接原因：我们对着已经停止处理的 iAP 栈重传了 12 次

```
16:51:00.6  TX StartIDPS(5702)
16:51:01.6  重传 #1
   ...      每秒一次，车机连 ACK 都不回
16:51:11.7  重传 #11
16:51:12.2  Connection reset by peer   ← 车机掐链路，屏幕冻住
```

健康车机回 ACK 是 20~50ms（整晚日志无例外）。
**20055 起**：最老未确认帧超过 3 秒就主动放手，不再灌重传。

### 5. 「静默时长」不能预测结果（我一度搞错）

曾以为"重连前必须静默 ≥20 秒"，把整晚数据摊开就碎了：

```
长会话 154s → 静默 2.3s → 成功     长会话 153s → 静默 3.1s → 失败
长会话 324s → 静默 2.7s → 成功     静默 52.1s        → 仍然 NO_SYN
```

静默时长不是自变量，车机自身状态才是，而我们读不到那个状态。
→ 20054 那条 20 秒规则**已整段撤销**，别在代码里找它。

### P0：自动重连（0 次成功）

```
01:03:30 1dfcc363  iAP 全通（5703 收到）→ 进 WIFI 阶段
```

说明卡在请求/关联那一侧，而 CarWith 大约 20 秒收走进程。

**下一步**：在这段加周期诊断（当前 SSID、activeNetwork、地址是否就绪、每次 NetworkCallback），
用一次真机复现定位到底卡在哪一半。不要再靠猜。

### P1：车机死机是否已被 20055 挡住（未验证）

`peer stopped acknowledging Nms ago` 且随后**没有** `Connection reset by peer`、车机不冻。

### P2：断 Wi-Fi 会让车机死机（iPhone 不会）

整晚未分析。已知：掐手机 Wi-Fi 属于"链路突然消失"，与 iPhone 的正常断开不是一类事件。

### P3：CarWith 放弃后没有任何组件再重试

它重开进程约 4 次就停手，之后必须人工介入。

## 七、11-04 续查：P0 的真根因是"重试链被超时静默掐死"（build 20056）

### 先更正我昨晚说错的两句话

1. **"卡在 Wi-Fi 请求阶段、12 秒零进展"** —— 错。Wi-Fi 早就 ready 了：
   `Wi-Fi callbacks ready; interface=wlan0`、`IPv4=1 IPv6=1` 在 Wi-Fi 阶段开始后 0.8 秒就打出来了。
   真正没有进展的是**之后的 Bonjour 端点发现**。
2. **"被 CarWith 收走"** —— 也错。那 12 秒结束时的资源释放级联是我们**自己**解开的。
   失败时刻精确等于 `浏览开始 + 15.000 秒`，那是 `ReceiverDiscovery.await()` 的窗口，
   两次失败分别是 15.002 秒和 15.000 秒，不可能是巧合。

### 两个失败样本的完整时间线（`1dfcc363` / `b96b8bdd`）

```
iAP 全通（aa00/aa01/aa02/aa03/aa05、4e09/4e0a/4e0d/4e0e/4e0c 往返正常）
5703 parsed security=2 channel=149        ← 车机只给网络参数
Handoff input=5703 networkReady=true endpointReady=false   ← 从头到尾没有 4301
stage WIFI → Wi-Fi ready（0.8s）
Bonjour hint browse started _raop / _hap / _mfi-config / _airplay   ← 四个浏览都起来了
……  15 秒内 _airplay 一个候选都没有（成功样本里只要 82 毫秒）……
Control invitation accepted as candidate   ← 车机反过来敲我们发布的 _carplay-ctrl 端口
……  仍然只等 Bonjour ……
浏览开始 +15.000s  ReceiverDiscovery 关闭 → 资源级联 → 会话结束
```

对照成功样本 `e8a7250a`：同样是 5703、同样没有 4301，但 `_airplay._tcp.` 在浏览开始后 **82 ms** 就出现，
于是正常进 PAIR 并出流。

### 根因：`TimeoutCancellationException` 被当成"父协程取消"

`TimeoutCancellationException` **是** `CancellationException`。而重试循环的第一条是：

```kotlin
catch(t:kotlinx.coroutines.CancellationException){throw t}
```

于是"发现器自己到点"被读成"整条链被放弃"，直接 rethrow，**没有任何重试**。
证据不是推理，是日志的**缺失**：

| 该出现的行 | 5 份真车日志里的出现次数 |
|---|---|
| `session resources released`（`attempt()` 收尾无条件打印） | **0** |
| `failure:` / `failure stack:`（重试循环的失败分支） | **0** |
| `stage RETRY`（进入等待重连） | **0** |

也就是说：**重试循环从来没有重试过一次**。17:03 那三次看似"连续重试"的会话，
全部是 CarWith 重新拉起的外部实例（上一次收尾后 0.4 秒、3.3 秒），
CarWith 一旦放弃，就再也没有任何东西会来拉起我们——这正好解释 P0"0 次成功"。

### 20056 改了什么

| 位置 | 改动 | 为什么 |
|---|---|---|
| `NetworkHandoffPipeline.open()` | 发现器超时在 `ensureActive()` 之后转成 `SocketTimeoutException` | 只有真正的父协程取消才该是取消；本地截止时间必须是一条普通失败 |
| `SessionController` 重试循环 | 先 `ensureActive()` 问上下文：真的死了才退出，还活着就按失败处理并进入 RETRY | 这是兜底：整条链路上 `withTimeout` 很多，逐个改不现实 |
| `ReceiverDiscovery` | 每 3 秒心跳（found/seen/pending/resolving/services）；每道静默丢弃候选的门都单独打一行 | 15 秒黑箱必须能自己说话：`found=0` 是车机没广播，`found>0 但 ready=false` 是我们筛掉了 |
| `CarPlayControlPublication` | 邀请日志补上 peer 与请求头**名**（不记录值） | 判断"邀请能否当端点"需要先知道它带不带 features/pk |
| 测试 | 新增 `resolverDeadlineWithoutDeclaredRouteIsNotCancellation` | 钉住"本地截止不得以取消的面目上抛"这条契约 |

全量 1179 条单元测试通过（含原有的 `endpointDeadlineIsFailureButParentTimeoutRemainsCancellation`，
它要求的"父协程真超时仍然是取消"没有被破坏）。

### 还没做、但已经有证据的下一步（P0.5）

车机不广播 `_airplay`、又自报 `carPlayStartSession=false`（明确表示它不会主动发 4301），
这两件事同时成立时，**协议上没有任何合法端点来源**——除了那条邀请：
它已经过了 `GET /ctrl-int/1/connect` + `AirPlay-Receiver-Device-Id` + 同链路校验，
而且来源就是车机自己。

用 `邀请地址:7000` 当端点能不能走通，卡在安全路由这一关：`startReady=false` 时
`SecurityRouting` 要求 `endpointSource==DISCOVERY` **且**必须有 feature evidence，
而邀请目前给不出 TXT 里的 features。所以这一步要先看 20056 打出来的邀请头名——
如果里面有 `features`/`pk`，这条路就能闭合；否则得另找证据源。**在没有真机日志之前不动它。**

### 20056 复测要点

1. 断开一次，**全程不碰手机与车机**，只等。
2. 日志里必须第一次出现 `stage RETRY` 和 `failure: SocketTimeoutException Bonjour endpoint deadline`——
   出现了就说明重试链活着了（这是本轮唯一的成功判据）。
3. 后续应该看到 `attempt` 序号递增的背靠背会话，周期约 19 秒（15 秒发现 + 2 秒间隔 + 握手）。
4. 车机真的缓过来（约 45~60 秒）时，那一次应该直接出流。
5. 如果出现 `Runtime iAP degraded` 之外的新失败，先看心跳行：`found=0` 与 `found>0` 指向完全不同的两个方向。

## 八、11-05 真车实测：第一次自动重连成了，但功劳是 CarWith 的

### 六段会话 = 六个进程

| 会话 | 时刻 | 时长 | 结果 |
|---|---|---|---|
| `f62866ac` | 21:42:04 | 21.1s | WIFI 阶段放弃（车机没广播） |
| `ace26fe5` | 21:42:28 | 18.5s | 同上 |
| `5e03d14a` | 21:42:50 | 50.9s | **出流**（浏览开始 1.05 秒就发现车机） |
| `79960bfb` | 21:43:44 | 17.9s | **出流**（video=130 帧 / RTP 400 包），被 CarWith 掐断 |
| `744dc2d0` | 21:44:06 | 6.2s | 车机 RTSP 主动 EOF，我们收尾 |
| `af362ca3` | 21:44:15 | 13.1s | 卡在 5702（车机 9.6 秒不 ACK），随后车机黑屏重启 |

`logcat` 里六个不同的 PID、六次 `onCreate`，**一次 `onDestroy` 都没有**。

### 谁在重试：不是我们，是 CarWith

```
21:42:25.753 teardown begin/end            ← 我们收尾
21:42:25.769 am_foreground_service_stop    ← 我们自己停了服务
21:42:25.791 UcarSM: CMD_DISCONNECT_CAST   ← CarWith 才反应
21:42:25.822 carlife need reconnect:true, start reconnect, remaining count:4
21:42:28.875 am_proc_start ... CarlifeConnectService   ← 3 秒后重新拉起
```

`status.failed = (stage == FAILED)`，所以服务会自停 → CarWith 判定断开 → 它自己重连。
**进程一次都没活过一轮，我那个 `while(isActive)` 重试循环依然从未执行。**

而且这次能定位到"判成终止性失败"这个结论，是靠**反推**的：`diagnostic.log` 里 `failure:` 依然 0 条，
因为进程在我们写完日志之前 13 毫秒就被 SIGKILL 了（异步落盘队列还没刷）。

### 昨晚的疑问有了答案：车机真的没广播

> **⚠️ 本节结论已作废，见第九节。** 下面的推断成立的前提是"我们确实在听"，
> 而这个前提是错的：那几轮尝试都发生在**手机锁屏**期间，我们当时听不见任何组播。
> 保留原文是为了记住这个错误——`found=0` 只说明"我们没收到"，不说明"车机没发"。

```
Bonjour still searching after 3000ms:  found=0 seen=0 pending=0 resolving=false services=[]
Bonjour still searching after 12006ms: found=0 seen=0 pending=0 resolving=false services=[]
```

`found=0` 且 `services=[]` —— 不是被我们的筛选门丢掉，是**车机这一轮根本没广播 `_airplay`**。
而第 3 次尝试在浏览开始后 **1.05 秒**就拿到了。

结论：车机冷启动后广播 `_airplay` 大约要 **45 秒**；我们的窗口是 15 秒，于是每 18~21 秒放弃一次、
放开 Wi-Fi、被 CarWith 杀一次、3 秒后再从蓝牙重来一遍。第一次"自动重连成功"是第 3 次撞上了那个时刻。

### 那次黑屏是谁的错：CarWith 的强杀，不是我们的重传

```
21:43:41.937 NotifOffBroadcastReceiver: com.miui.carlink.action.DISCONNECT_CAST_ACTION
21:43:41.938 CarlinkSM: receive SEND_DISCONNECT event, dispatch CMD_DISCONNECT_CAST
→ forceStop（SIGKILL），我们来不及发 TEARDOWN

21:44:12.369 channel source=event-reader EOFException RTSP header   ← 车机的 RTSP 自己关了
21:44:15.625 新一轮 iAP：SYN/AUTH/4e0e/4e0c 全部正常
21:44:19.024 TX 5702 → 车机从此不再 ACK，重传到 28.033（10 次）
21:44:28.688 放弃 → 用户看到黑屏 → 车机自动重启
```

要点：车机的 AirPlay 栈在 **21:44:12.369** 就已经死了（RTSP 主动 EOF），比黑屏早了 16 秒。
后面那 10 次重传是**对着一个已经死掉的协议栈**在喊，不是把它喊死的。

### 20057 / 20058 改了什么

| build | 改动 | 依据 |
|---|---|---|
| 20057 | 收到车机邀请时，发现窗口 15s → 再等 45s，不再放开 Wi-Fi 租约 | 邀请证明车机在场；广播只是晚到。省掉整轮杀-重启 |
| 20058 | 失败原因与"终止/可重试"判定写进 logcat（`CarVexFail`） | 文件永远写不到，13 毫秒就被杀 |

`endpointWaitMs` 一并放到 75 秒罩住 15+45；没有邀请时 15 秒照旧抛错，不会拖慢"车机不在场"。

### 被证伪的一条设想（P0.5 关闭）

邀请请求的头只有 `host, user-agent, airplay-receiver-device-id`，**没有 `features`/`pk`**。
所以"拿邀请当端点"无法满足 `SecurityRouting` 对 `DISCOVERY` 源必须带 feature evidence 的要求。
这条路在没有别的证据源之前**关掉**，不再讨论。

### 20058 复测要点

1. 车机开机后**第一次连接就应该成**（一次等到 45 秒，而不是三次各等 15 秒）。
2. 若某次失败，`adb logcat -d -s CarVexFail` 会直接给出异常类型与终端判定——这是本轮最需要的证据。
3. `stopCast` 之后车机是否还黑屏：那是 CarWith 强杀导致的，我们只能在"少杀几次"上做功，不能消除。

## 九、11-05 深夜更正：慢的真因是手机锁屏，不是车机

大哥一句话把第八节推翻了：

> 一开始那么久是因为 手机没解锁 他不会自动连接。现在的断开重连开始不行。车机照样死机

日志完全支持这个判断，而且是**逐毫秒**支持：

```
22:02:16.1xx  ScreenOn:false          ← 手机黑了
22:02:19      found=0                 ← 第 1 次尝试，全程听不见
22:02:40      found=0                 ← 第 2 次
22:03:01      found=0                 ← 第 3 次
22:04:52.986  ScreenOn:true           ← 亮屏
22:05:00      found=1 → 端点到手（7 秒）← 第 4 次，一次就成
```

同一段日志里心跳每 3 秒都在打点，说明**进程没被冻结、浏览也一直挂着**。
所以"车机冷启动要 45~136 秒才广播"这个结论是错的：它把"我们聋了"记在了车机账上。

### 为什么聋了，以及为什么聋一次就完蛋

Android 的 Wi-Fi 在灭屏后可以整片丢掉组播帧，`WifiManager.MulticastLock` 是唯一开关
（它作用在**整个接口**上，即使 mdns 的套接字开在系统进程里也管用）。
而清单里 `CHANGE_WIFI_MULTICAST_STATE` 一直声明着，代码里却从没用过——权限是留给这件事的，功能没写。

更糟的是 mDNS 的两种"丢了不补"叠在一起：

- 车机（响应方）的公告是**无条件组播**，发几次就退到两小时一次，丢掉的不会补发；
- 我们（查询方）的查询间隔从 1 秒指数退避到一小时，浏览跑得越久问得越少。

于是"锁屏那几分钟没听见"不是延迟，是**直接丢掉一整轮连接机会**——只能等 CarWith 的 40 秒预算到点、
把我们 SIGKILL、再重启一轮。这就是大哥看到的"一开始那么久"。

### 20059：别再对着死掉的 iAP 栈重传

第二段断开后那次（`0b966876`，11.2 秒就死）走的是这条路：

```
5702 发出（车机还占着上一段会话）→ 车机不 ACK → 重传 9 次 → Connection reset by peer
→ IllegalStateException: iAP link changed during bootstrap → 车机黑屏
```

上一轮我写的"3 秒不 ACK 就放手"护栏**从未生效**：`sendCsm` 是阻塞的（要等所有 slot 被 ACK 才返回），
`Bootstrap` 里的 poll 循环根本轮不到执行；而 `oldestUnackedAgeMs()` 用的是 `sentAtNanos`，
每次重传都会刷新，永远上不到 3 秒。

20059 把它改成在**阻塞的发送循环内部**用 `lastAckProgressNanos` 度量——衡量"车机多久没理我们"，
而不是"某一帧重传了多久"。3 秒放手，静默失败退避 6 秒。同时把发现窗口按 40 秒预算调成 15+15。

### 20060：把耳朵补上

| 改动 | 为什么 |
|---|---|
| 浏览期间持有 `MulticastLock` | 灭屏丢组播是接口级行为，只有这个开关能关掉 |
| 每 6 秒重开一次 `_airplay` 浏览 | stop/start 会立刻重新发问，车机**必须**回答；这是把车机叫醒的唯一手段，也是把"我们聋了"和"车机还没起来"分开的唯一办法 |
| 状态行加 `screenOn` / `multicastHeld` | 这两种 `found=0` 在日志里长得一模一样，这两个字段一眼分开 |
| 解析失败限次重试（4 次） | `seen` 去重表会把解析失败的名字永久拉黑，车机再重播也不解析了 |

### 20060 复测判据

1. **锁屏状态下**发起连接，`Bonjour still searching` 那行必须是 `screenOn=false multicastHeld=true`，
   并且 `found` 最迟在重开浏览后的一个周期内 > 0。若 `multicastHeld=false`，说明小米拒了这把锁，
   那就得改用"重开浏览"单独扛（它本身也能救回来）。
2. 断开重连时，若车机还占着上一段会话，期望看到
   `iAP peer stopped acknowledging Nms ago while sending`，**且之后没有** `Connection reset by peer`。
3. 若仍黑屏，`adb logcat -d -s CarVexFail` 会给出异常类型与终端判定——这是唯一能穿过 SIGKILL 的信道。

### 5702 静默护栏（20059）验证通过

装 20061 时 SIGKILL 掉正在投屏的进程，正好复制出"车机占着旧会话"的现场：

```
14:47:25.026  TX 5702
14:47:26.027  TX 5702   (重传)
14:47:27.029  TX 5702   (重传)
```

### 量出来的代价：失败一次赔 90 秒

```
22:47:19  连车机 7000 → ECONNREFUSED     ← 车机 AirPlay 服务整个不在了
22:47:25  5702 发出，车机不 ACK           ← 服务回来了但占着旧会话
22:48:18  CarWith 40 秒预算到点，CAST_FAILURE
22:48:23  5702 终于 ACK                   ← 旧会话释放
22:48:37  CAST_SUCCESS
```

机制：我们失败 → 放开 `WifiNetworkSpecifier` → CarWith 判定"投屏结束" → `releaseCastCore`
→ 命令车机拆接收端 → 车机把无线 CarPlay 子系统重启一遍（60~90 秒）。
**我们的失败率越高，这 90 秒就越常发生——循环有一半是我们自己踩出来的。**

另一条被划掉的路：CarWith 的 `DISCONNECT_CAST_ACTION` 广播到 `forceStop` 只有 **1 毫秒**
（`21:43:41.937` → `.938`），"抢在杀之前发 TEARDOWN"不可行，代码里也没有任何地方监听它。

### 20061：车机重开 IDPS 时重走识别

`RuntimeIap` 轮询循环里那句裸 `check(linkEpoch==authorizedEpoch)` 是 `Check failed.` 的来源：
车机把 epoch 从 1 推到 3，断言一进来就炸，`fail()` 把整条 iAP 判死。改成 epoch 变了就
重走一遍识别（最多 4 次），判定类 `check` 全部补上可读原因。**尚未被真车触发验证。**

### 20062：租约抬到会话级

`CarNetworkLease` 持有网络回调，跨"尝试"存活；某次尝试失败只关它自己的资源，网络留着，
下一次尝试直接复用（连 specifier 都不再发）。只有整段会话真的结束才释放。

**验收判据**：断开重连时，日志里应出现
`reusing the Wi-Fi lease already held across attempts`，
并且 CarWith 侧**不再**出现 `releaseCastCore` / `carlinkDisconnected`；
重连耗时应从 ~90 秒降到个位数秒。

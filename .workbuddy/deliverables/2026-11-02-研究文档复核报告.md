## 一、结论先行（三句话）

1. **交接文档的"技术骨架"是可信的**——我逐条 grep 复核了它的关键行号，`SecurityRouting.kt:48/91`、`BootstrapSecurity.kt:58/64`、`AirSession.kt:479/542/563/1043` 全部一字不差。
2. **但它"为什么只能走 SAP"的论证依据不足**——把 mingtu 判死的两条闸门（必须给 `pi`/`pk`、地址必须严格相等）在 `research/` 全库里**找不到证据出处**，而 `pk` 恰恰被规范明令"不得当身份或信任锚"。这两条是**本地安全发明**，不是固件要求。
3. **真车若走 SAP，黑屏的第一嫌疑不是 CTR 计数器，而是帧头**——SAP 分支只写了 128 字节头里的 3 个字段，**连 `+0x05` 的关键帧位都没写**。这一条比交接文档 §6.3 列的四个排查点更靠前。

## 三、重大发现 1：判死 mingtu 的两条闸门，证据缺位

### 3.1 gate 的真实条件

`BootstrapSecurity.kt:42-70` 的 `gate()` 共 14 道关，其中三道决定了 mingtu 的命运：

| 行 | 条件 | 说明 |
|---|---|---|
| `:55-57` | `pi` 必须存在、非空、1..1024 字节 | 来自 TXT `pi` |
| `:58-59` | `pk` 必须存在且**恰好 32 字节** | 来自 TXT `pk` |
| `:63-64` | Bonjour 地址必须与 iAP2 地址 `contentEquals` | 严格字节相等 |

mingtu 日志（`device-log.txt:170`）显示 `keyPresent=false`，`:179` 显示同一端点的两个地址是 **IPv4 `192.168.0.1` vs IPv6 链路本地 `fe80::cafe:...`** —— 两条全中。

### 3.2 规范怎么说

| 规范条款 | 原文要点 | 出处 |
|---|---|---|
| R-3.8（MUST） | `pk`/`pi`/`gid` 在 24A446 里只出现在**构造 TXT** 的代码中；实现不得声称"车机会读/会认" | `research/protocol/airplay_mdns_discovery/spec/03-txt-schema.md:33` |
| R-3.9（MUST NOT） | **不得把 `pk`、`pi`、`gid` 当作已认证身份或信任锚**；发现路径没有校验它们的证据 | 同文件 `:36` |
| R-10.7（MUST NOT） | 同上，重申不得作为信任锚或身份凭证 | `spec/10-cache-and-security.md:28` |
| `OPEN-MDNS-13` | `pk`/`pi`/`gid` 能否作为身份或配对依据 → **状态 OPEN** | `spec/08-open-items.md:20` |

而 `sameAddress`（地址严格相等）这条要求，我在**整个 `research/` 目录里 grep 不到任何出处**（唯一命中 `contentEquals` 的地方是在讨论 CFData 长度，与地址无关）。

### 3.3 这意味着什么

- 这两条闸门**不是固件行为**，是 Android 实现的本地安全发明（`git log --follow BootstrapSecurity.kt` 只有「初始导入」和「加回落开关」两次提交，中间没有任何"对应固件地址"的提交）。
- 它们的效果是：**一台可能本来能走成熟 HAP 路线的车，被推到了零验证的 SAP 路线上。**
- 更要紧的是：**TXT 缺 `pk` 在原理上不该阻止 HAP**。HAP 走的是 pair-setup 的 M1–M6 现场交换公钥（见 `26-airplay-security-branches.md:64`「CU 为 false 时创建 legacy client 并消费 PeerPublicKey」），并不依赖 mDNS 里那份 TXT `pk`。

> ⚠️ 这不是说"删掉 gate 就能连上"。`SecurityRouting.kt:83-84` 还有一道更硬的拦截（`requiresUnsupportedCuEntry`），以及 `:67-68` 的 F80 拦截。mingtu 因为 F38=1、F80=0 恰好都不触发。但把"本地发明"当"结构上不可能"，是交接文档最大的推理跳跃。

## 四、重大发现 2：P0 判据里预期的那行日志，大概率会看错

交接文档 §6.2 让你期待看到：

```
Experimental HAP gate=pk_missing pi=absent pk=absent bonjour=fe80::… iap2=192.168.0.1:7000
```

但 `gate()` 的检查**顺序**是：

```
disabled → start_ready → transport → source → network → endpoint_not_validated
→ auth_missing → auth_context_stale → auth_unsigned → no_f38
→ pi_missing(:55) → pk_missing(:58) → endpoint_missing → port_mismatch
→ address_mismatch(:64) → device_id_missing → peer_mismatch
```

**`pi` 先于 `pk`**。如果 mingtu 的 TXT 既没给 `pi` 也没给 `pk`（日志只证明了 `pk` 缺，`pi` 没打），新包打出来的会是 **`gate=pi_missing`**，而不是文档预期的 `pk_missing`。

→ 看到 `pi_missing` 不代表改动没生效、更不代表构建坏了。**这是文档预期行写错了，不是代码问题。**

## 五、重大发现 3：帧头逐字段对账（U-3 的真正嫌疑）

规范出处：`research/protocol/airplay_video_channel/analysis/02-screen-record-format.md`
（代码注释里写的「第 07 章 §2.6」**并不存在**——`airplay_fairplay_crypto/spec/07-*` 用的是 `R-7.x` 编号。真出处是上面这份 `02` 章。）

### 5.1 帧记录（type=0）

| 偏移 | 规范语义 | HAP 路径 `VideoWire.frame` | SAP 路径 `AirSession:1306` |
|---|---|---|---|
| `+0x00` u32 | body 总长（含附加长度） | `nals+16` ✅ | `encrypted.size` ✅ |
| `+0x04` u8 | type = **0** | 0 ✅（零填充） | 0 ✅（零填充） |
| `+0x05` u8 | bit7 附件 / bit4 同步附件 | 关键帧→`0x10` ✅ | **未写 → 恒 0** ❌ |
| `+0x08` u64 | 网络时间戳 | `presentationNtp` ✅ | `ntp` ✅ |
| `+0x10` u64 | 来自 `[流对象+0x3e0]`，**语义未定** | `monotonicNs`（无依据） ⚠️ | `timestamp`（无依据） ⚠️ |
| `+0x18` u32 | 恒 0 | 0 ✅ | 0 ✅ |
| `+0x1c` u32 | 可选尾段长度 | 0 ✅ | 0 ✅ |
| `+0x20` u64 | 第二次时间转换结果 | `captureNtp` ✅ | **未写** ❌ |
| `+0x28` u64 | 第一次时间转换结果 | **未写** ❌ | **未写** ❌ |
| `+0x58` u64 | 与 `+0x20` 同值 | `captureNtp` ✅ | **未写** ❌ |
| `+0x60`–`+0x7f` | **帧间隔数组 u16×16**（ms，≥65536 写 0xffff） | **未写** ❌ | **未写** ❌ |

**SAP 分支只写了 `0x00/0x08/0x10` 三个字段，其余全是零。**

其中 `+0x05` 最关键：它是接收端判断"这一帧能不能开始解码"的标志位。**没有关键帧位，车机有充分理由一直等 IDR，画面就是黑的。** 这比交接文档 §6.3 列的四点（et 装配、头布局、CTR 连续性、streamId）都要前置。

### 5.2 配置记录（type=1）

`VideoWire.config()`（`core/Wire.kt:143-153`）对账：

| 偏移 | 规范 | 代码 | 判定 |
|---|---|---|---|
| `+0x00` | 配置载荷长度 | `avcc.size` | ✅ |
| `+0x04` | type = 1 | `1` | ✅ |
| `+0x06` | 基值 `0x12` + 条件位 | `0x12 or 0x04` = `0x16` | ✅（有 cryptor 置 bit2） |
| `+0x07` | 恒 1 | `1` | ✅ |
| `+0x08` u64 | **网络时间戳** | **未写** | ❌ |
| `+0x10`/`0x14` | 几何 float | `w`,`h` | ✅ |
| `0x10..0x3c` 共 10 个 float | 含源矩形 | 只写了 `0x28/0x2c`、`0x38/0x3c` 各 **2 个** | ⚠️ |

代码注释写的是「源矩形是 `0x20` 与 `0x30` 各四个 float」，**但实际 `putFloat` 落在 `0x28` 和 `0x38`，每个矩形只写了 2 个值**。注释与代码不符，源矩形实际只填了一半（缺 origin 两个分量）。

### 5.3 保活记录

`VideoWire.keepAlive()` 写 `+0x04 = 2`、`+0x7c` float 长度、不加密。
与 `02-screen-record-format.md:80-86`（`0x2519b07a8..7bc`、`0x2519b07e0` 写 `+0x7c`）一致 —— **这条是对的**，可以放心。

> 注：该记录在规范里叫"统计构造分支"（type 2/5），注释称"保活"是同一路径的用途命名，字段层面没错。

## 六、重大发现 4：`et=16` 值对，但前提被越过了

### 6.1 值是对的（这条交接文档没问题）

`29-control-setup-request-branches.md:48` 给出内部类型 → wire `et` 的映射：

> 按 holder 内部类型选择 wire `et`：**类型 8→16**、4→32、1→2。

`26-airplay-security-branches.md:50` 给出 `AuthenticationType` 优先级：**F26 → 类型 8（MFi）**。mingtu 置了 bit26。

→ **类型 8 → `et=16`，完全对上。** 交接文档选 `et=16` 有实锤依据。

### 6.2 但固件还有一道前置，我们主动越过了

同一行（`29:26` 与 `29:48`）明确：

> `et`/`ekey`/`eiv`：**key holder 存在，且 endpoint 不支持 CoreUtils pairing/encryption 时进入**；CoreUtils 支持为真也跳过。

mingtu 日志 `:183`：`cu=true directCu=true` → **按固件，这台车的 SETUP 根本不该带 `et` 块**。

我们的做法是：它声称支持 CU，但 gate 过不去 → 强走 SAP 并塞 `et=16`。这是一个**有意识的、但未在提交信息里声明的偏离**（`AGENT.md` §4 要求每次生产修改说明"新实现如何与固件对齐"）。

这在逻辑上是个矛盾组合：**车机说"我支持 CU"，我们回"不，你要走 MFi"。** 车机是否买账，只能真机验。

### 6.3 一个成本极低、价值极高的对照实验

**拿一台真 iPhone 连 mingtu，看它能不能出 CarPlay 画面。**

| 结果 | 推论 | 该做什么 |
|---|---|---|
| iPhone **也连不上** | 车机 F38 是虚报，CU 路径本就不通 | SAP 方向正确，继续 P0 |
| iPhone **能连上** | CU 路径本可行，是我们的 gate 过严（pk/pi/地址） | **优先修 gate，而不是投 SAP**——HAP 是唯一有声有画面验证过的路线 |

这一步不需要任何代码改动、不需要买设备，却能直接决定后面几百行改动的方向。**比任何静态分析都值钱。**

## 九、给下一个 Agent 的三条纪律（我加在交接文档之外）

1. **任何 gate 条件都要能指到固件地址或 docset 条款。** `pk`/`pi`/`sameAddress` 三条指不到，就该被当作"本地策略"标注，而不是"车机行为"。
2. **看到 `pi_missing` 不要以为改坏了。** 它排在 `pk_missing` 前面。
3. **帧头不要只写 `0x00/0x08/0x10`。** 规范里 `+0x05`、`+0x20`、`+0x28`、`+0x58`、`+0x60..0x7f` 都有明确语义或明确"未定"，`+0x05` 尤其不能缺。

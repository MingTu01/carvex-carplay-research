**三处推翻此前判断的地方：**

## 三、断线后连不上：根因定位

### 3.1 两次断开的对比（决定性证据）

| | 第一次断开 10:12:45（会话 `114f95c0`） | 第二次断开 ~10:23:11（会话 `9d419e19`） |
|---|---|---|
| `User disconnect; whole-session stop requested` | ✅ 有 | ❌ **没有** |
| `AirPlay whole-session TEARDOWN begin` | ✅ 有 | ❌ **没有** |
| `TEARDOWN ... status=200` | ✅ 车机回 200 | ❌ 没发 |
| 之后能否重连 | ✅ 4 秒后 `9d419e19` **成功** | ❌ 之后 **9 次全部 NO_SYN** |

**这就是全部答案**：走完 TEARDOWN 的断开，车机把会话释放了，下次能连；没走 TEARDOWN 的断开，车机以为老会话还活着，于是**永远不给新会话发 SYN**。

### 3.2 失败态长什么样

成功时车机先开口：

```
iAP detection RX=ff550200ee10      ← 车机先发 Detect
iAP detection TX=ff550200ee10
iAP frame RX 80/116/0/0/16         ← 车机发 SYN
iAP synchronized session=1 version=2
```

失败时我们对着空气喊：

```
iAP first-byte deadline 2000ms; sending Detect    ← 干等 2 秒没人理
iAP NO_SYN: no peer SYN within 7000ms; tearing the link down
```

**关键点**：9 次失败中，RFCOMM 都是 **90 毫秒内连上**的（`10:23:14.342 → 10:23:14.432`）。
→ **蓝牙物理层没问题，是车机的 iAP2 应用层不应答。** 这排除了配对、信号、UUID 缓存等一堆嫌疑，直指"对端会话残留"。

### 3.3 三种可能的残留来源（按可能性排序）

1. **App 侧旧 RFCOMM socket 没关干净**（最可能）
   会话"凭空消失"时没有任何 teardown 日志，旧 `BluetoothSocket` / AirPlay 控制 socket 可能仍被持有。车机那条 SPP 通道只认一个对端，新连接在 L2CAP 层能接上，但数据仍被路由到旧通道。
2. **车机侧 CarPlay 会话半开**
   车机仍认为 AirPlay 会话在跑，等我们发后续请求，因此不启动新的 iAP2。
3. 宿主（CarWith）先撤了绑定，把会话从我们脚下抽走
   日志里 10:23:14 起每次尝试都由 `[entry] Intent extras: manufacturer=..., usb_type=..., bindVersion=...` 拉起 —— 说明**是 CarWith 在疯狂重试**，不是用户手点。

> ⚠️ 注意 3.1 的第二次断开发生在**应用仍存活**的情况下（10:23:14 的新会话没有伴随 `应用已启动`），所以不是"进程被杀导致没来得及拆"。是某条**静默结束路径**绕过了 `disconnect()`。

### 3.4 后续无法自愈

从 10:23:21 到 10:28:10（近 5 分钟）9 次尝试全部 NO_SYN，车机始终没恢复。说明这**不是等一会儿就好的超时**，必须有人主动清场（车机端关 CarPlay / 重启车机，或手机端关开蓝牙）。

## 六、必须修正的两份文档结论

1. **交接文档 §3** 说"真车走 HAP 是结构性走不通，SAP 是唯一选择"——
   实测：**SAP 这条确实通**。但请注意，`pk` 缺失仍然是 gate 唯一的拦路条件，而 `pi` 和地址都过了。所以"放宽 `pk` 就能试 HAP"这个可能性**依然存在**（见上一份报告），只是现在**没有动力去试了** —— SAP 已经出画面了。
2. **我上一份报告的帧头结论**要降级：`+0x05` 关键帧位缺失**没有**导致黑屏。它仍是证据缺口，但不是当前瓶颈。

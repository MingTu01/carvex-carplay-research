## 一、这次改了什么（一句话）

真车走的是 MFi/SAP，而音频代码在 SAP 下**直接抛异常**（`AirSession.kt:1043`）。现在让它改用 MFi 流密钥 + AES-CTR 发包；**HomeKit 路线一个字节都没动**。

## 二、证据依据：哪些是闭合的，哪些是猜的

按 `AGENT.md`「没有证据时不得关闭 OPEN 项」，先把边界摆清楚。

### 2.1 有闭合证据的部分（可以照做）

| 事实 | 依据 |
|---|---|
| 音频消息 M = 2B seq + 4B timestamp + 4B 第二字段 + 载荷；12 字节头 = `0x80`+PT+这 10 字节 | 音频 spec **R-2.6**（`A02.5`/`A09.1`/`0x226e689e0`） |
| AES-CTR：等长、无 tag、无填充、计数器 128 位大端跨调用连续 | `06-frame-crypto-aes` **R-6.1**（`A-22`/`A-41`） |
| 流密钥 KDF：`SHA512("AirPlayStreamKey"‖dec(id)‖K)[0:16]`，IV 同构 | `STATUS.md:21-22`（`A-46`，参考实现与独立计算一致） |
| 该 KDF 在本项目已可用于真车 | 屏幕流在同一台 mingtu 上出画面（18312 帧），走的就是 `mfi.streamCipher` |
| `et=16` = 内部类型 8（MFi） | `29-control-setup-request-branches.md:48` |

### 2.2 仍是 OPEN、我们在没有抓包时做的选择（必须写明）

| 未知 | 我们的选择 | 若真机不响，先查这里 |
|---|---|---|
| **MFi 音频的线上 profile**：密码输入是否只覆盖 payload | 头部明文、只加密 payload——由 R-4.1「密码输入为 M[10+g:T]」推得，但那条是 CoreUtils provider 的证据 | `MediaAudioPackets.sapPacket` 的切片 |
| 音频流 KDF 用的是哪个整数 id | 用本地生成的 `id`（即 SETUP 里的 `streamConnectionID`），与屏幕流的做法一致 | `AirSession.kt` 里 `mfi?.streamCipher(id)` |
| 麦克风方向的输入密钥 | **不实现**，SAP 下不声明 `input` | 日志会打 `microphone not offered` |
| RED 冗余块 + CTR 的组合 | **不提供**（`offeredRed=false`） | 车机若强行开 RED，会明确拒绝而不是发坏包 |

> 媒体抓包缺失是 docset 的既有缺口（`OPEN-3`/`OPEN-10`，`verify.py` 对 C10 显式 SKIP）。所以这次改动**不能声称"已验证正确"**，只能声称"按已闭合的证据做了最小改动，并让真机日志能定位偏差"。

## 三、改动清单（5 个文件）

| 文件 | 改动 |
|---|---|
| `core/MediaAudioPackets.kt` | 新增 `sapPacket()`：12 字节头 + `cipher.update(payload)`，等长、无 tag、无 nonce 尾 |
| `CarPlayCompressedAudio.kt` | 新增可选 `sapCipher`；非空时走 CTR 封包、跳过要求 ≥36 字节的 ChaCha 诊断、打印一次加密模式 |
| `AirSession.kt` | SAP 下用 `mfi.streamCipher(id)` 建密钥；不再无条件抛异常；麦克风在 SAP 下不宣告 input；不提供 RED；PCM 分支明确失败 |
| `MediaAudioPacketsTest.kt` | 新增 3 个用例：头部一致性/等长、计数器跨包连续、非法输入拒绝 |
| `CompressedAudioTimestampTest.kt` | 反射构造参数 14→15（新增 sapCipher 传 null），否则 `single{}` 抛 `NoSuchElementException` |

### 关键代码

```kotlin
// MediaAudioPackets.sapPacket —— 头部沿用 HomeKit 分支，只换密码学
val header = ByteBuffer.allocate(12).order(BIG_ENDIAN)
    .put(0x80).put(pt).putShort(seq).putInt(ts).putInt(0).array()
return header + cipher.update(payload)   // CTR：等长，无 tag，无 nonce 尾
```

## 五、真机验证：该看哪几行

装 `CarVex_xiaomi_debug_20013.apk`（包名 `com.baidu.carlife.xiaomi`），**先重启车机**（清掉上次残留会话），从 CarWith 发起连接。

### 5.1 成功路径应该依次出现

```
Audio crypto category=1 mode=AES-CTR(MFi/SAP) redEnabled=false payloadOnly=true tagBytes=0 nonceTail=0
Audio SETUP fields category=1 spf=... controlPort=... input=absent dataPort=none offeredRED=false
Audio SETUP accepted category=1 type=102 dataPort=<非空> RED=null ...
Audio streamID category=1 type=102/media id=<数字>
Compressed encoder ready name=<编码器> category=1 codec=AAC_LC
Compressed RTP category=1 type=102 codec=AAC_LC packets=1; audible acceptance pending
```

**判据**：`Audio SETUP accepted` 出现且有 `dataPort`，说明车机接受了音频流；随后 `packets` 递增说明在发包。**此时才算"链路通了"，声音另算。**

### 5.2 如果没声音，按这个顺序查（一次只改一个变量）

| 现象 | 含义 | 下一步 |
|---|---|---|
| `Audio SETUP` 返回非 200 / 被拒 | 车机不接受 SAP 下的音频流描述 | 抄下 SETUP 请求体与响应码，对照 R-2.2 的字段条件 |
| `microphone not offered` 出现但 category=3 没声音 | 预期行为：SAP 下没麦克风 | 正常，先看 category=1（媒体） |
| `Audio crypto ... mode=AES-CTR` 有，但 `packets` 停在 1 | UDP 发送异常 | 看下一行 `Compressed audio category=N failed:` |
| `packets` 正常递增、车机没声 | **加密切片或 KDF id 不对** | 先试「加密 12 字节头 + payload」，再试「按响应 streamID 派生密钥」 |
| 车机报 RED 不一致后关流 | 车机强行开 RED | 抄下 `response=` 值，再决定是否实现 RED+CTR |

### 5.3 要一并抄回来的现场

- `Audio SETUP fields` 与 `Audio SETUP accepted` 两行
- 首包前 32 字节（如果后续要加诊断）
- 车机侧是否有任何音频相关提示
- **音频这一轮不要同时改断线清理**，否则出问题分不清是哪个造成的

## 六、这一轮**没有**做的事（明确的边界）

1. **断线后车机残留会话**（CarWith 关闭 → 无 TEARDOWN → 必须重启车机）——这是独立的 P0 级问题，改动小但影响大，建议**下一轮单独做**。理由：`AGENT.md` §7.4「一次只验证一个假设」。
2. **麦克风**（SAP 输入方向）。需要反向 KDF 与 `CarPlayMicReceiver` 的 CTR 解密分支。
3. **PCM 直通**（type 100 的 PCM 分支）。当前明确失败而不是发错包。
4. **RED + CTR**。SAP 下不提供。
5. 帧头剩余字段（`+0x28`、`0x60-0x7f`）。本车不阻塞，属证据补齐。

## 七、给下一个接手者的一句话

音频这条路现在**从"必然抛异常"变成了"会真的发包"**。如果真机静默，问题几乎肯定在「加密切片」或「KDF 用的 id」这两处二选一——因为密码学算法、头部布局、计数器语义这三样都是有闭合证据的，不该是嫌疑对象。
